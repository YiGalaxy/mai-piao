# 第二轮优化实施记录

日期：2026-10-24。对应 [初始评估](第二轮业务与技术栈优化评估.md)。本轮在已有预约保留改造上继续修改工作区，未提交、部署或执行用户数据库迁移。

## 已实施

| 领域 | 变化与作用 |
| --- | --- |
| 演示入口 | 控制器限定 dev profile，且必须显式开启；改为 `/movie/admin/demo` 管理路径。网关白名单收窄为具体只读接口和登录注册 POST。已有演示场次拒绝在线清理/覆盖。 |
| 交易调用 | 关键 Feign 写调用检查 `R` 的业务成功标记；HTTP 200 + `R.fail` 会中断事务，避免后续继续出票或确认退款。 |
| 支付身份 | 按订单唯一约束创建稳定 paymentNo，支付意图由独立 Bean 的 REQUIRES_NEW 事务提交，再调渠道。并发和响应丢失后复用原身份，不延期、不随意换渠道。 |
| 支付核验 | 以订单快照核验用户、金额、状态和支付期限；支付查询验证归属。回调核对渠道、订单、交易号、金额和状态，日志仅用于审计，合法 FAILED→SUCCESS 不被旧日志吞掉。 |
| 支付恢复 | 定时主动查单；过期 PENDING 尝试渠道关单，只有明确 CLOSED 才关闭本地。渠道未知保持未决，成功结果经全局事务推进。已取消订单的迟到收款创建仅退款、不释放座位的退款意图。 |
| 退款投递 | 订单 REFUNDING 状态和 outbox 同一本地事务提交，定时投递；支付侧先独立提交稳定 refundNo。响应丢失不丢申请，重复投递复用同一退款。 |
| 退款确认 | 仅支持实付金额整单退；先查询原退款，仅明确 NOT_FOUND 才发起。UNKNOWN/PROCESSING 保留身份继续查询；明确 SUCCESS 且有渠道退款号才结清，明确 FAILED 停止自动查询。迟到收款退款不改已取消订单、不重复释放库存。 |
| Redis 补偿 | 支付/退款新增 seat_synced、seat_released 持久标记，定时补偿事务提交后的 Redis 确认/释放。订单侧通过全局锁核验已提交状态，远端失败不标记完成。退款中的订单不会再次确认 SOLD。 |
| 售票规则 | 选座和自动分配校验场次可售状态、开售/抢购时间、开演时间及每单限购，数据库库存占用 SQL 也约束窗口与数量。后台删除场次改为停售。 |
| 排队保护 | 热点场次回源使用 single-flight 合并和短暂失败退避；准入 Lua 根据共享 inflight 数量计算剩余配额，多调度器共享上限。令牌核验、消费和移除 inflight 由 Lua 原子执行。 |
| Mock 渠道 | 补齐查询、关单和退款查询；预创建与退款使用固定身份。支付账本本地持久化，关单与付款互斥；写盘失败停止报告成功，重启可恢复已持久状态。 |
| 压测证据 | 修正历史报告与工具文案：分配锁座不是成交，接口平均耗时不是排队等待，约 22k req/s 只表示售罄拒绝路径。原始历史日志未改。 |
| 管理审计 | 在 common-web 增加自定义 `@AdminAuditLog` 和 Spring AOP，统一记录有本地业务库的管理员写操作、结果、耗时和脱敏参数；审计写入失败旁路告警，日志按服务本地数据库保存。queue-service 保持无数据库设计。 |

支付查单、退款 outbox 投递、Redis 补偿使用 Spring `@Scheduled` 配合 ShedLock，默认约 10 秒一轮；部分任务还要求记录至少 30 秒未更新，恢复不是即时的。退款未知结果按退避时间继续查询。

上一轮稳定预约 token、固定截止时间、创建资格 CAS、Seata 结果未知时保留座位与原身份重试继续保留，详见 [下单失败与座位保留](优化建议-下单失败与座位保留.md)。

## 数据库与运行要求

已有库需要先执行升级，详细步骤见 [SQL 说明](sql/README.md)。核心文件：

- `sql/schema/07_order_reservation.sql`：缺少预约表时补表。
- `sql/migrations/08_trade_reliability.sql`：已有库一次性增量迁移，先对账处理重复 orderNo 的支付记录。
- `sql/migrations/09_admin_audit_log.sql`：四个业务库补齐管理员操作审计表，使用幂等的 `CREATE TABLE IF NOT EXISTS`。
- 新库直接使用当前 schema；不能将包含 DROP 的初始化脚本用于旧库升级。

Mock 支付默认账本路径为 `data/mock-pay/state.json`，相对于进程工作目录。建议启动时设置固定绝对路径，例如 `--maipiao.mock-pay.state-file=D:/maipiao-local-state/mock-pay/state.json`；容器运行须挂载持久目录。文件需由服务账号可读写。发生写盘失败后，修复存储并重启，不能继续把内存状态当作持久成功。

Mock 是单实例开发渠道，不支持多个进程共享 JSON 文件，也不能作为真实渠道资金证明。当前 compose 主要编排基础设施，不会自动部署 Mock 服务。Mock 回调默认直接访问 pay 服务的 `http://127.0.0.1:9005/pay/notify/MOCK`，不经网关；真实渠道接入还需验签、网络入口与渠道协议适配。

## 验证结果

2026-10-24 本轮最终验证：

- `mvn -q test -Dreservation.integration=true -Dtrade.integration=true`：退出码 0，11 个测试类共 63 项，失败 0、错误 0、跳过 0。
- 其中临时容器集成测试共 12 项：8 项预约基础设施测试使用 MySQL 8.4、Redis 7.4、Seata 2.2；4 项交易基础设施测试使用真实 MySQL。覆盖全局事务提交/回滚、全局锁、双调度器准入、令牌竞争、支付意图并发与独立提交、实际增量迁移及退款补偿字段。
- 其余测试覆盖 HTTP 200 业务失败、乱序/重复回调、稳定支付号、退款响应未知、outbox 重投、Redis 补偿失败不误标完成、Mock 付款关单竞争及持久化恢复等。
- `maipiao-web`、`maipiao-admin-web` 的 `npm run build` 均通过；仍有超过 500KB 的 chunk 提示，尚未拆包优化。
- 测试使用独立临时容器，已自动清理；没有对用户库做故障注入。测试通过不代表已验证真实支付渠道或生产级吞吐。

## 后续仍需处理

1. **支付中取消的完整协调**：当前保留迟到收款退款兜底，尚未完成“渠道明确关单/查单 → 再取消与释放”的完整协议，用户仍可能先扣款再退款。需明确 PAYING 状态、渠道未知时等待策略及超时通知。
2. **长期未决运维**：支付/退款未知、明确失败、outbox 和 Redis 补偿积压需要监控告警、人工核对/恢复入口；管理员基础操作审计已落地，跨服务汇总、查询页面、保留期和告警平台仍需完善。
3. **Redis 全量恢复**：尚未完成恢复闸门、预约与数据库/渠道统一核对、重建后再开放售卖的演练；队列重排不能代替交易预约恢复。Redis Cluster 的 Lua 同槽设计也未完成。
4. **入口容量**：通用网关限流、排队容量上限、熔断及资源隔离尚需按实测容量配置。
5. **累计实名限购**：当前是每单数量限制，尚未实现账号/证件跨订单累计限购及实名校验。
6. **真实渠道与完整压测**：仍使用 Mock；需要渠道沙箱、完整交易链路故障验证及压测。现有历史数据仅覆盖分配和拒绝路径。
7. **工程治理**：Flyway 迁移、依赖版本治理、前端拆包、结构化指标与发布回滚流程仍需推进。当前 Java/Spring、MySQL、Redis、RocketMQ、Vue 技术方向保留，没有为扩展技术栈新增中间件。

以上是当前落地边界，初始评估中的建议并未全部完成。
