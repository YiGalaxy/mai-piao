## 一、定时任务、线程和 ShedLock

### 0. 项目使用了什么技术栈？

**示例回答：**

> 后端使用 Java 21、Spring Boot、Spring Cloud/Alibaba，数据访问使用 MyBatis-Plus，持久化数据库是 MySQL，Redis 用于排队、准入、位图锁座和缓存，RocketMQ 用于订单超时定时消息，Seata 用于多个数据库服务的全局事务协调，Spring AOP 用于管理员操作审计。前端主要是 Vue 3，部分由 AI 辅助开发。我主要负责后端，项目定位是学习项目。

### 0.1 为什么在订单超时场景选择 RocketMQ，而不是 Kafka？

**示例回答：**

> 这里的直接需求是按每笔订单的截止时间触发一次检查，RocketMQ 5 直接提供定时消息能力，发送时可以传绝对投递时间。Kafka 也可以构建业务方案，但通常还要配合数据库到期扫描、延迟 Topic 或外部调度器，未来投递和恢复逻辑会不同。这个选择是基于当前场景的实现便利，不代表 Kafka 不能做业务消息，也没有证明 RocketMQ 在所有场景都更快。

### 1. 定时任务是新开线程，还是和其他线程抢占？

`@Scheduled` 由 Spring 调度器调用。每次触发不会为每次任务永久新建一条线程，也不会在 HTTP 请求线程里执行。当前项目没有自定义 `TaskScheduler`，同一个服务实例默认使用 Spring Boot 的调度线程池；默认调度池大小为 1，因此同一实例内的几个定时任务通常轮流执行。

服务整体并不是只有一条线程：

```text
HTTP 请求       -> Web 容器请求线程池
RocketMQ 消费   -> RocketMQ 客户端消费线程
定时任务        -> Spring 调度线程
```

不同服务实例运行在不同 JVM 中，各自有自己的线程池。支付服务的定时线程不会直接占用订单服务的 Java 调度线程，但如果部署在同一台机器、访问同一个数据库或大量调用订单接口，仍可能通过 CPU、内存、连接池和下游请求间接影响其他服务。

### 2. 一个调度线程够不够？

不能直接保证够用。当前任务按批次扫描，例如支付座位同步每批最多 50 条，订单过期扫描每批最多 200 条。单条记录可能包含数据库查询和远程调用；如果一轮处理速度低于新增待处理记录的速度，就会积压。

当前实现的优点是限制了单批量，并且每条记录单独捕获异常，不会因为一条坏数据终止整个批次；不足是没有针对同一补偿任务配置独立业务线程池，也没有通过压测证明处理上限。

后续优化可以把“定时扫描”和“记录处理”分开：调度线程只领取有限记录，交给有界业务线程池；队列满时保留未完成记录，远程调用设置超时，重复处理仍必须依靠业务幂等。单纯把调度线程数改大，主要解决不同定时任务相互等待，不能自动提升单个扫描任务的吞吐量。

### 3. `@Scheduled` 这一行是什么意思？

代码：

```java
@Scheduled(fixedDelayString = "${maipiao.pay.seat-sync-ms:10000}")
```

拆开解释：

- `@Scheduled`：让 Spring 自动调用这个方法。
- `fixedDelayString`：本次方法执行结束后，再等待指定时间。
- `${maipiao.pay.seat-sync-ms:10000}`：优先读取配置 `maipiao.pay.seat-sync-ms`，没有配置时使用默认值 `10000`。
- `10000` 的单位是毫秒，即 10 秒。

例如任务 12:00:00 开始，12:00:03 结束，下一次大约在 12:00:13 开始，而不是 12:00:10 强行开始。

### 4. `@SchedulerLock` 的三个参数是什么意思？

```java
@SchedulerLock(
    name = "pay-seat-sync",
    lockAtMostFor = "PT5M",
    lockAtLeastFor = "PT5S"
)
```

- `name`：这一个定时任务的共享锁名。多个支付服务实例使用同一个名字时，同一时刻通常只有一个实例执行。
- `lockAtMostFor = "PT5M"`：最多持有 5 分钟。实例拿锁后突然宕机，锁过期后其他实例还能继续执行。
- `lockAtLeastFor = "PT5S"`：至少保持 5 秒，防止任务执行很快时多个实例频繁抢锁。

`@SchedulerLock` 只协调多个定时扫描实例，不能协调 RocketMQ 消费者和定时扫描，也不能代替业务幂等。真正的正确性仍要放在数据库状态条件、座位归属和可重复的释放逻辑上。

源码：[SeatSyncJob.java](../maipiao-service/maipiao-pay/src/main/java/com/maipiao/pay/job/SeatSyncJob.java)、[SchedulerLockConfig.java](../maipiao-common/common-redis/src/main/java/com/maipiao/common/redis/config/SchedulerLockConfig.java)。

## 二、幂等、重复执行和座位同步

### 1. 幂等到底是什么？

定义是：**同一个业务操作执行一次或多次，最终业务结果相同。**

```text
幂等：设置座位为 SOLD:ORD001
第一次：座位 -> SOLD:ORD001
第二次：座位 -> SOLD:ORD001

非幂等：库存减 1
第一次：100 -> 99
第二次：99 -> 98
```

### 2. 支付后 Redis 同步失败，下一轮怎么知道还要处理？

支付表有 `seat_synced` 字段。定时任务查询：

```sql
SELECT *
FROM t_pay_payment
WHERE status = 1
  AND seat_synced = 0
  AND update_time < ?
LIMIT 50;
```

`seat_synced = 0` 表示本地还没有记录“座位同步完成”；`seat_synced = 1` 的记录不会再被扫描。定时任务重新查到同一条支付记录后，继续使用这条记录里的同一个 `order_no`，不会重新生成订单号。

### 3. Java 和 Lua 分别负责什么？

Java 层负责流程控制：

1. 查询 `seat_synced = 0` 的支付记录。
2. 查询订单当前状态。
3. 只有已支付或已完成才调用确认座位。
4. 远程调用明确成功后才把 `seat_synced` 改为 1。
5. 失败时保留 0，供后续重试。

Lua 层负责 Redis 内部的操作：

```lua
redis.call('HSET', ownerKey, seatIndex, 'SOLD:' .. orderNo)
redis.call('ZREM', delayKey, orderNo)
```

同一订单重试时，`orderNo` 仍来自同一条支付记录，所以仍然写入 `SOLD:ORD001`。`HSET` 是设置固定目标值，`ZREM` 重复删除也不会影响其他订单。Lua 的原子性保证脚本内命令不会被其他 Redis 命令插入；原子性和幂等性是两个不同概念。

### 4. 当前实现的边界

当前 `seat_confirm.lua` 直接设置 `SOLD:订单号`，没有在写入前严格检查座位当前是否仍属于本订单；座位接口也没有把返回的确认数量与订单座位数做严格比较。因此可以说“同一订单重复写固定状态不会再次扣库存”，但不能把它夸大成“所有 Redis 异常都能自动恢复”。更完整的设计应该让 Lua 返回明确结果码，并校验：

```text
座位属于当前订单       -> 可以确认
座位已经是当前订单 SOLD -> 视为重复成功
座位属于其他订单       -> 冲突，不能覆盖
找不到订单座位集合     -> 异常，不能直接标记成功
```

### 5. Redis 超时和业务冲突要区别处理

- Redis 连接超时、网络异常：结果可能未知，保留 `seat_synced = 0`，延迟重试并告警。
- 座位属于其他订单：不是暂时故障，不能无限重试；应保留未完成状态，核对 Redis、MySQL 座位账本并告警。

当前代码对异常分类还不够细，主要是捕获异常、记录日志、让下轮继续扫描，这是需要后续增强的地方。

源码：[SeatSyncJob.java](../maipiao-service/maipiao-pay/src/main/java/com/maipiao/pay/job/SeatSyncJob.java)、[seat_confirm.lua](../maipiao-service/maipiao-seat/src/main/resources/lua/seat_confirm.lua)、[PaymentMapper.java](../maipiao-service/maipiao-pay/src/main/java/com/maipiao/pay/mapper/PaymentMapper.java)。

## 三、RocketMQ 定时消息和定时扫描

### 1. 为什么两种方式都用？

两者职责不同：

```text
RocketMQ 定时消息 -> 正常情况下及时触发
定时扫表         -> 消息发送失败、服务宕机或漏消费后的兜底
```

项目用 RocketMQ 5 的绝对时间投递能力，在订单原截止时间后约 1 秒投递订单号。定时扫表默认约 60 秒一次，所以只用扫表可能多占座几十秒；但消息发送失败或进程在发送前宕机时，扫表仍能发现过期订单。

两条路径都调用统一的取消服务。即使消息和扫表同时触发，`@SchedulerLock` 只减少多个扫描实例的重复，真正防止错误取消和重复释放的是：

1. 订单状态只允许 `PENDING_PAY -> CANCELLED`。
2. 状态更新带原状态条件，影响行数为 0 表示别人已经先处理或订单已进入其他状态。
3. Redis 释放脚本按订单归属匹配，重复释放没有额外效果。

### 2. 取消和支付同时到达怎么办？

支付只允许 `PENDING_PAY/PAYING -> PAID`，取消只允许 `PENDING_PAY -> CANCELLED`。两个操作通过行锁和带状态条件的 SQL 串行化：

```text
取消先成功 -> 订单为 CANCELLED，迟到支付不能复活订单，进入退款流程
支付先成功 -> 订单为 PAID，取消条件不成立，不释放座位
```

如果取消先成功但渠道已经扣款，支付服务关闭本地支付记录并创建退款单，不能重新出票，也不能重复释放已经释放的座位。

### 3. 重复退款回调如何幂等？

退款单用 `payment_no` 唯一约束和 `INSERT IGNORE` 防止同一支付产生多笔退款单。退款成功使用条件更新：

```sql
UPDATE t_pay_refund
SET status = 2,
    channel_refund_no = ?
WHERE refund_no = ?
  AND status IN (0, 1)
  AND refund_amount = ?;
```

第一次影响 1 行；重复回调影响 0 行，再读取已有退款记录，核对金额和渠道退款号一致后视为已经处理，不再次退款。

源码：[OrderTimeoutProducer.java](../maipiao-service/maipiao-order/src/main/java/com/maipiao/order/mq/OrderTimeoutProducer.java)、[OrderTimeoutConsumer.java](../maipiao-service/maipiao-order/src/main/java/com/maipiao/order/mq/OrderTimeoutConsumer.java)、[OrderTimeoutJob.java](../maipiao-service/maipiao-order/src/main/java/com/maipiao/order/job/OrderTimeoutJob.java)、[RefundMapper.java](../maipiao-service/maipiao-pay/src/main/java/com/maipiao/pay/mapper/RefundMapper.java)。

## 四、ZSet 排队和一次性准入

### 1. 排队和准入分别做什么？

用户先进入：

```text
queue:wait:{scheduleId}
```

这是 Redis ZSet，用户 ID 是 member，进入时间是 score。重复加入使用 `addIfAbsent`，不会改变原排位。

调度器根据剩余座位和当前 inflight 人数，每约 200 毫秒放行一小批队首用户。Lua 脚本一次完成：

```text
取 ZSet 队首
从等待队列移除
生成短期准入 token
记录在途用户
给 token 设置 TTL
```

锁座前必须消费有效 token；消费脚本会校验 token、删除 token、从 inflight 移除用户。这保护的是后面的锁座、订单服务、数据库，使大量请求主要停留在 Redis 队列，不会同时打穿核心链路。

### 2. 队列 token、锁座 token 和 XID 不一样

| 标识 | 作用 |
| --- | --- |
| queueToken | 一次抢购准入资格，消费后失效 |
| lockToken/orderNo | 一次座位预约及后续订单业务标识，重试沿用 |
| XID | 某一次 Seata 全局事务尝试的标识 |

不能把 queueToken 当 JWT，也不能把 XID 当订单号。

源码：[QueueService.java](../maipiao-service/maipiao-queue/src/main/java/com/maipiao/queue/service/QueueService.java)、[queue_admit.lua](../maipiao-service/maipiao-queue/src/main/resources/lua/queue_admit.lua)、[queue_consume.lua](../maipiao-service/maipiao-queue/src/main/resources/lua/queue_consume.lua)。

## 五、Bitmap、Lua 和 MySQL 的双层防超卖

### 1. Bitmap 和 Lua 的准确职责

Bitmap 只表达座位是否被占用：`0` 可用，`1` 不可用。它不表达座位属于谁，所以还需要 owner Hash、订单座位 Set 和过期 ZSet。

`seat_lock.lua` 先检查所有目标座位，只要一个冲突就返回失败；全部空闲才一次性设置 Bitmap、owner、订单座位集合和过期记录。Lua 只修改 Redis，**不负责写 MySQL**。

### 2. MySQL 为什么还要再校验？

Redis 可能丢数据、与数据库短暂不一致，或者请求在不同阶段失败。订单创建时 MySQL 做最终校验：

```sql
UPDATE t_event_session
SET locked_seat = locked_seat + #{count}
WHERE id = #{sessionId}
  AND locked_seat + sold_seat + #{count} <= total_seat;
```

并且具体座位要满足：

```sql
UPDATE t_event_session_seat
SET status = 1,
    lock_order_no = #{orderNo}
WHERE ...
  AND status = 0;
```

如果库存更新影响行数为 0，或具体座位更新行数不等于请求数量，就抛异常回滚下单事务，不创建成功订单。数据库条件更新是最终防超卖关卡，不能因为 Redis 显示可用就继续下单。

### 3. Redis 已锁座但 MySQL 下单失败怎么办？

Redis 不参加 Seata AT，数据库回滚不会自动撤销 Redis。当前改进后的预约流程会持久化预约状态：

```text
明确回滚 -> RETRYABLE，原期限内保留座位供同 token 重试
结果未知 -> PROCESSING + XID，先问 TC，禁止直接释放
确认可关闭 -> CLOSED，再走按 owner 校验的 Redis 释放
```

如果结果未知就提前释放，其他订单可能拿到座位，而原事务随后提交，造成数据库与 Redis 归属冲突。

源码：[seat_lock.lua](../maipiao-service/maipiao-seat/src/main/resources/lua/seat_lock.lua)、[MovieInternalController.java](../maipiao-service/maipiao-movie/src/main/java/com/maipiao/movie/controller/MovieInternalController.java)、[SessionMapper.java](../maipiao-service/maipiao-movie/src/main/java/com/maipiao/movie/mapper/SessionMapper.java)、[OrderCreationService.java](../maipiao-service/maipiao-order/src/main/java/com/maipiao/order/service/OrderCreationService.java)。

## 六、Seata、预约状态和 XID

下单入口不是简单地“开一个 Seata 事务然后看有没有订单行”。持久预约表保存 token、用户、场次、座位、固定截止时间、状态、请求摘要和 XID。

典型流程：

```text
登记 PREPARING
    -> Redis 锁座成功，发布 RESERVED
    -> CAS 抢执行权，写 PROCESSING + XID
    -> 执行库存、座位账本、优惠券、订单分支
    -> 明确提交：SUCCEEDED
    -> 明确回滚：RETRYABLE
    -> 结果未知：保持 PROCESSING，之后查询 XID
```

同一个 lockToken 重试时仍使用同一个业务标识，但新一轮事务可以拥有新的 XID。`PROCESSING` 记录必须独立持久化，否则业务事务回滚后，恢复任务就不知道原尝试存在。

## 八、回答项目题的固定模板

每道题按以下顺序回答，避免只说组件名：

```text
1. 先说并发或故障场景
2. 说明哪条 SQL、Lua 或状态条件决定谁成功
3. 说明成功后写入的持久状态
4. 说明失败、超时、重复执行时怎么恢复
5. 最后主动说清当前实现边界
```

例如回答“Redis 锁座失败后怎么办”：

> Redis Lua 负责原子检查和占用，MySQL 条件更新负责最终防超卖。若 MySQL 明确回滚，预约可以在原截止时间内保持并用同一个 token 重试；如果 Seata 结果未知，则保留 `PROCESSING + XID`，先查询全局结果，不能直接释放 Redis，避免其他订单抢到后原事务又提交。

### 问题 1：请介绍项目和你认为最有技术难度的部分

**示例回答：**

> 这是一个个人学习用的仿猫眼票务平台，我主要负责后端，前端借助 AI 辅助完成。项目支持选场次、选座、创建订单、支付和超时取消。我认为最有挑战的是抢票时的并发控制：请求先经过排队准入，再由 Redis Lua 原子锁座，创建订单时还要由 MySQL 条件更新做最终校验。项目还处理重复下单、支付与取消竞争以及事务结果未知等情况。它是学习项目，完整成交容量还没有通过生产级压测验证。

### 问题 2：几万人抢票时，系统怎样避免请求直接打到订单服务和数据库？

**示例回答：**

> 抢购场次先通过 Redis ZSet 排队，score 保存进入时间。调度器根据剩余座位和当前在途人数，周期性放行一批队首用户，并通过 Lua 原子发放短期准入 token。锁座接口必须消费有效 token 才继续，因此不是所有等待用户都会同时进入锁座和下单链路。ZSet 控制排队顺序，token 控制准入人数；这和 MySQL 最终防超卖是不同层次的保护。

### 问题 3：系统如何决定谁能锁到一张具体座位？

**示例回答：**

> 对目标座位的竞争由 Redis 中的 Lua 脚本串行仲裁。脚本先检查所有目标座位的 bitmap 位；如果有一个已占用，整笔请求失败；如果全部空闲，才一次性设置占用位和 owner。并发请求在 Redis 中按脚本执行先后竞争，先通过检查并写入的请求成功。之后创建订单时还要通过 MySQL 的库存和座位状态条件更新，不能只相信 Redis。

### 问题 4：Bitmap 和 Lua 分别保存什么、解决什么问题？

**示例回答：**

> Bitmap 的一位表示座位当前是否可选，0 是可选、1 是占用；它本身不记录占座订单，所以项目还用 owner Hash 保存座位归属，并用订单座位 Set 保存一个订单占了哪些座位。Lua 不负责写数据库，它把 Redis 内部的“检查是否空闲”和“设置占用及归属”放在一次脚本执行中，防止两个请求都读到空位后分别写成功。MySQL 的持久化校验在后续订单事务里完成。

### 问题 5：Redis 显示有座，但 MySQL 库存条件更新影响行数为 0，怎么办？

**示例回答：**

> 以 MySQL 的条件更新结果为准。影响行数不符合预期时抛出业务异常，回滚整个下单数据库事务，不创建成功订单。Redis 不参加 Seata AT，数据库回滚不会自动撤销 Redis；预约层会记录明确回滚或结果未知。明确回滚时在原截止时间内保留预约供同 token 重试，到期后安全关闭并释放；结果未知时先根据 XID 查询，不能直接释放。

### 问题 6：Redis 已锁座、数据库订单事务失败，为什么不马上释放座位？

**示例回答：**

> 如果数据库明确回滚，用户可能还会在原预约期限内用同一个 token 重试，所以项目把预约标记为 `RETRYABLE` 并暂时保留座位。如果事务结果未知，可能实际上已经提交；此时释放座位会让另一个订单拿走，原事务后来提交就造成冲突。因此未知时保留 `PROCESSING + XID`，查清 TC 结果后再决定重试或释放。预约过期并确认可以关闭后，回收任务才释放 Redis。

### 问题 7：你说的幂等是什么？项目里怎么体现？

**示例回答：**

> 幂等是同一个业务操作执行一次或多次，最终业务结果相同。支付后 Redis 确认使用同一条支付记录中的同一个 orderNo，把 owner 设置为固定的 `SOLD:订单号`，并移除该订单的超时记录。网络超时后即使 Lua 已成功但响应丢失，下一轮仍使用相同 orderNo 重试，不会再扣一次库存。Java 用 `seat_synced` 记录补偿是否完成：只有远端明确成功才改为 1，否则保留 0。

**需要主动补充的边界：**当前确认脚本无条件写 `SOLD:订单号`，上层也没有严格校验返回座位数。因此它说明了重复写固定状态的幂等思路，但 owner 冲突和 Redis 座位集合缺失仍需加强校验。

### 问题 8：为什么重试时知道还是同一个订单号？

**示例回答：**

> 定时任务重新查到的是原来的支付记录，记录中的 `order_no` 没有重新生成，所以每次都把同一个订单号传给确认接口。锁座 token 在这个流程里沿用为订单号。重复请求不是依靠 Lua 记住上次操作，而是依靠持久记录提供同一业务标识，再将 Redis 写成相同的目标状态。

### 问题 9：取消任务和支付回调同时到达，怎样避免互相覆盖？

**示例回答：**

> 订单状态迁移带原状态条件。取消只允许 `PENDING_PAY -> CANCELLED`，支付只允许 `PENDING_PAY/PAYING -> PAID`。数据库串行化同一订单行的竞争，只有符合当前状态的一个更新成功。取消先成功时，迟到支付不复活订单，转入退款；支付先成功时，取消条件不成立，不会释放座位。

### 问题 10：取消先成功，但支付渠道已经扣款，怎么办？

**示例回答：**

> 订单保持已取消，不重新出票，也不恢复成已支付。支付服务把本地支付记录关闭并创建退款单，之后按原退款单号向渠道退款。因为取消流程已经释放过座位，迟到支付退款不应再次释放座位，所以使用不释放座位的退款类型/标记。

### 问题 11：退款回调重复到达，为什么不会重复退款或重复修改订单？

**示例回答：**

> 退款单按 payment_no 唯一，避免同一支付重复创建退款单。退款成功通过带 `refund_no`、可迁移状态、金额条件的 CAS 更新。第一次影响一行并推进到成功；重复回调影响零行后查询已有记录，核对金额和渠道退款号一致，就不再重复迁移订单数据库状态。Redis 释放接口可能再次调用，但其 owner 校验使重复释放不会影响其他订单。

### 问题 12：为什么 RocketMQ 延时消息和定时扫表都保留？

**示例回答：**

> RocketMQ 定时消息是主触发路径，让订单到期后更及时地进入检查；定时扫表是兜底，处理消息没发出、服务在发送前宕机或漏处理等情况。两条路径共用订单取消状态机，取消的带状态 SQL 和 Redis owner 校验负责并发下的正确性。ShedLock 只减少多个扫描实例重复工作，不负责协调 MQ 消费者和扫描任务。

### 问题 13：`@Scheduled` 和 `@SchedulerLock` 分别做什么？

**示例回答：**

> `@Scheduled` 让 Spring 定时调用方法。`fixedDelayString` 表示方法执行完成后再等指定时间；`${maipiao.pay.seat-sync-ms:10000}` 表示读取配置，未配置时默认 10000 毫秒。`@SchedulerLock` 是 ShedLock 的分布式调度锁：name 是任务名，`lockAtMostFor` 防止实例宕机后锁长期不释放，`lockAtLeastFor` 设置最短持锁时间。它只协调同一个定时任务的多实例执行，不是业务正确性的最终保障。

### 问题 14：微服务中每个服务的线程池是共用的吗？定时任务会影响其他服务吗？

**示例回答：**

> 每个服务实例运行在自己的 JVM 里，各自管理 Web、调度和消费线程，不会跨 JVM 共用同一个 Java 线程池。一个实例的定时线程不会直接占用另一个服务实例的线程，但可能通过共享主机 CPU、数据库连接池、Redis 或远程接口产生间接影响。项目当前没有自定义调度池，同一支付实例的定时任务默认共享一个调度线程，所以慢任务会拖延该实例的其他定时任务。

### 问题 15：一个调度线程处理积压够吗？

**示例回答：**

> 不一定。当前座位同步每批最多 50 条，订单超时任务每批最多 200 条，但一条记录可能包含数据库和远程调用。如果积压产生速度长期超过处理速度，就会变慢；当前没有完整交易容量压测，不能声称一定够用。我会监控积压量、最老记录等待时间、单批耗时和下游错误率，再决定是否用有界业务线程池并发处理，并保证拒绝的任务仍留在待处理状态。

### 问题 16：Seata 能不能回滚 Redis？XID 是什么？

**示例回答：**

> 项目中的 Seata AT 协调的是接入数据源代理的数据库分支，不会自动回滚 Redis。XID 是某次 Seata 全局事务的标识，预约表在 `PROCESSING` 状态保存 XID。结果未知时恢复任务拿 XID 向 TC 查询；明确提交后标记成功，明确回滚后标记可重试，状态仍未知就保留预约，不误释放座位。

### 问题 17：抢购 token、锁座 token、JWT 是同一种 token 吗？

**示例回答：**

> 不是。queueToken 是短期的一次性准入资格；lockToken 是某次预约的稳定业务标识，并沿用为订单号用于重试和资源归属；JWT 是登录身份凭证，包含用户身份等声明并由签名验证。XID 则标识某一次全局事务尝试。每种 token 的签发者、用途、生命周期和校验位置都不同，不能互相替代。

### 问题 18：JWT 是加密的吗？拿到别人的 JWT 能不能使用？

**示例回答：**

> 常见 JWT 的 Header 和 Payload 是 Base64URL 编码，不是加密；服务端根据 Header 和 Payload 重新计算签名并比较，另外校验过期时间、签发者等声明。签名只能保证内容没有被篡改，不能证明持有人就是合法用户；拿到他人的未过期 JWT 可能被冒用，所以还要使用 HTTPS、保护存储、校验订单资源归属，并在网关清理外部伪造的身份头。项目登出通过 Redis 黑名单在 JWT 到期前撤销 jti。

### 问题 19：项目为什么选 RocketMQ，而不是 Kafka？

**示例回答：**

> 项目选择 RocketMQ 的直接原因是订单超时取消需要按订单截止时间投递消息，RocketMQ 5 提供定时消息能力，能作为及时触发路径。Kafka 也能实现业务消息，但通常要另加定时调度、延迟 Topic 或数据库扫描来管理未来投递时间；这会改变实现复杂度和恢复方式。不能因此说 Kafka 不能做业务消息，也不能声称 RocketMQ 在所有场景性能更好。

### 问题 20：Java 锁能不能解决多实例抢同一座位？

**示例回答：**

> `synchronized` 和 `ReentrantLock` 只协调同一个 JVM 内使用同一把锁的线程。多服务实例有不同 JVM，彼此看不到对方的本地锁。项目通过 Redis Lua 协调 Redis 里的座位竞争，再用 MySQL 条件更新做持久层最终校验；业务状态 CAS 处理订单状态的竞争。即使使用 Redis 分布式锁，也不能替代数据库条件和业务幂等。

### 问题 21：为什么不能信任前端传来的票价？

**示例回答：**

> 前端价格只能用于展示，不能作为支付依据。管理员可能在用户选座后修改票档价格，或者客户端篡改请求金额。下单时服务端根据场次和座位票档重新计算原价，优惠券由用户服务按订单号和用户校验后锁定，订单保存应付金额快照；支付回调还要核对本地支付单、订单快照、渠道流水和回调金额。不能拿支付回调时的最新票价覆盖下单时的金额。

### 问题 22：JWT 是加密还是签名？登录态怎样注销？

**示例回答：**

> 项目使用的 JWT 主要是编码加签，不是把 Payload 加密。服务端用密钥重新计算 Header 和 Payload 的 HMAC 签名并比较，再校验过期时间、issuer 和用户声明。注销时把 JWT 的 jti 写入 Redis 黑名单，TTL 取剩余有效期，网关后续请求拒绝该 jti。JWT 只证明令牌签名有效，业务接口仍要核验订单、预约等资源属于当前用户。

### 问题 23：如果客户端伪造 `X-User-Id` 请求头，为什么不能直接相信？

**示例回答：**

> 身份头属于服务端信任边界内的数据，客户端可以任意构造。网关应先删除外部传入的身份头，验签 JWT 后再写入可信的用户信息；内部接口还需要网络隔离或服务间认证，不能只依赖一个可伪造的 header。下游订单查询、取消和预约操作仍要把资源 userId 与当前认证用户比对，防止水平越权。

### 问题 24：为什么管理员操作值得使用自定义 AOP 切面？

**示例回答：**

> 管理员修改场次、票档或订单时，需要统一记录操作人、目标资源、参数、结果和耗时。如果每个 Controller 手写日志，容易漏记且脱敏规则不一致。自定义 `@AdminAuditLog` 注解标记业务写方法，AOP 在方法进入和退出边界统一采集审计信息，并对密码、Token 等字段脱敏。审计写入失败只告警，不能让主业务因为日志系统故障失败。切面只做横切审计，不把核心业务状态迁移藏在切面里。

### 问题 25：Redis 重启或主从切换导致锁座数据丢失，项目怎样处理？

**示例回答：**

> Redis 支持 RDB/AOF，但仍可能因未刷盘数据、故障切换窗口、淘汰或误删丢失状态，所以不能把 Redis 当唯一事实源。订单创建时通过 MySQL 的库存、座位状态和订单归属条件做最终校验；Redis 位图可以根据数据库账本重建。重建期间要控制并发和售卖入口，避免一边重建一边按不完整位图放行。当前项目有按账本补种位图的机制，但 Redis 整体丢失后的完整在线恢复仍需要继续验证。

### 问题 26：Seata 的全局事务能不能直接协调 Redis 和支付渠道？

**示例回答：**

> 不能直接这么说。项目中的 Seata AT 主要协调接入代理的 MySQL 分支，并通过 Feign 传递全局事务上下文。Redis 和外部支付渠道不自动加入 AT。Redis 采用提交后同步、持久标记和补偿任务；支付渠道采用本地支付单、退款单、渠道流水和结果查询来处理重复通知与未知结果。`@GlobalTransactional` 不是所有外部资源的万能回滚按钮。
