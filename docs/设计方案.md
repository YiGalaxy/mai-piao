# 仿猫眼电影售票系统 — 设计方案与实施方案

## Context

**为什么做**：求职**作品集项目**（目标岗位：Java 后端校招 / 实习），复刻猫眼电影售票系统的**核心技术难点**，而非复刻界面。猫眼官方不公开完整技术栈，可确认的线索是：Java 微服务生态、Seata 分布式事务（AT/Saga）、Redis 高并发、选座交易系统按"冗余/隔离/监控"三原则设计，节假日峰值是平时 10 倍。本项目按这些线索反向设计一套可落地的等价架构。

**验收标准**：不是"能跑通"，而是**能在面试里被追问 30 分钟**，每个技术决策都能讲清"为什么这么选、否决了什么"。详见 §十七。

**要解决的五个核心问题**：
1. **选座并发** — 同一座位绝不能被两人同时锁定，超卖是致命 bug
2. **超卖** — 库存扣减的并发边界
3. **订单状态机** — 状态流转必须有守卫条件，终态不可逆
4. **支付幂等** — 回调会重复、乱序、延迟到达，处理不当会重复出票或吞钱
5. **百万级抢票** — 2000 张票对上百万用户，如何在网关层消化掉 99.8% 的无效流量

**范围**：微服务架构（9 个服务）+ Java 技术栈 + H5 用户端 + 影院管理后台 + 抢购排队层。支付先做自建 Mock 网关（策略模式预留支付宝沙箱实现）。

**展示方式**：本地 Docker Compose 跑全套 + 3 分钟录屏演示 + 高质量 README（不部署云服务器）。

**明确不做**：分库分表实际落地、K8s、多机房多活、灰度发布、真实短信/实名认证、XXL-Job、云服务器部署。

## 三、服务拆分与职责

| 服务 | 端口 | 职责 | 核心技术点 |
|---|---|---|---|
| `gateway` | 9000 | 统一入口、JWT 校验、路由、全局限流 | Gateway 过滤器 + Sentinel |
| `user-service` | 9001 | 注册登录、JWT 签发、用户信息、优惠券 | JWT 无状态 + Redis 黑名单 |
| `movie-service` | 9002 | 影片、影院、影厅、座位模板、场次排片、场次库存 | 库存扣减的并发边界 |
| `seat-service` | 9003 | 座位图查询、锁座/释放 | **Redis Bitmap + Lua 原子批量占位** |
| `order-service` | 9004 | 下单、订单状态机、超时取消 | 状态机 CAS + RocketMQ 延迟消息 |
| `pay-service` | 9005 | 创建支付、回调、流水、退款 | **四层幂等** + PaymentChannel 策略 |
| `admin-service` | 9006 | 影院/影厅/座位模板/排片录入、订单查询 | 后台独立鉴权（角色区分） |
| `mock-pay-gateway` | 9007 | **非业务服务**，模拟支付宝服务端 | 能主动触发重复/乱序/失败/验签错误回调 |
| `queue-service` | 9008 | 抢购排队、分批放行、售罄标记、熔断开关 | **Redis ZSet 排队 + 放行器 + 售罄快速失败** |

**公共模块**：`common-core`（统一返回体 `R<T>`、业务异常、枚举、雪花 ID）、`common-web`（全局异常处理、Feign 拦截器透传 `X-User-Id`、Swagger 配置）、`common-redis`（Redis/Redisson 配置、Lua 脚本加载器、Bitmap 工具类）。
**Feign 契约模块**：`maoyan-api` 存放所有 Feign 接口与 DTO，避免服务间循环依赖。

### 5.1 maoyan_movie（影片/影院/排片/座位账本）

|---|---|---|
| `t_movie_film` 影片 | id, name, en_name, poster_url, director, actors, duration, type, release_date, score, status(0待映/1热映/2下映) | `idx_status_release` |

| `t_movie_hall` 影厅 | id, cinema_id, name, hall_type(IMAX/3D/普通), row_count, col_count, **seat_template**(JSON 座位布局), status | `idx_cinema` |
| `t_movie_schedule` 场次 | id, film_id, cinema_id, hall_id, show_date, start_time, end_time, price, **total_seat, locked_seat, sold_seat**, status(0待开售/1售票中/2放映中/3已结束/4已取消), **rush_mode(0普通/1抢购)**, **rush_start_time**(开抢时刻) | `uk_hall_time(hall_id,start_time)`, `idx_film_date`, `idx_status_time` |

### 5.5 演示数据初始化（自己生成，不依赖猫眼真实 API）

**分工原则：静态小数据用 SQL 种子，海量数据用程序生成。**

| 数据 | 量级 | 生成方式 |
|---|---|---|
| 影片 | 24 部 | `docs/sql/seed_film.sql` 静态脚本 |
| 影院 | 8 家 | `seed_cinema.sql` |
| 影厅 + 座位模板 | 每影院 5 个厅，共 40 个 | `seed_hall.sql`，座位模板用 JSON |
| 用户 | 5 个测试账号 | `seed_user.sql`，密码统一 BCrypt(`123456`) |
| 优惠券模板 | 3 档（满50减10 / 满100减30 / 满200减80） | `seed_coupon.sql` |
| **场次排片** | 8 影院 × 5 影片 × 7 天 × 5 场 ≈ **1400 场** | **程序生成** |
| **场次座位** | 1400 场 × 约 120 座 ≈ **16.8 万行** | **程序生成** |

16.8 万行手写 SQL 不现实，因此实现 `admin-service` 的初始化接口 `POST /admin/demo/generate-schedule`。

**座位模板 JSON**（存 `t_movie_hall.seat_template`）：
```json
{
  "rows": 10,
  "cols": 12,
  "aisleCols": [4, 9],
  "brokenSeats": ["1-1", "1-12", "10-1", "10-12"],
  "coupleSeats": [["5-6", "5-7"], ["6-6", "6-7"]]
}
```
含义：10 排 12 列，第 4、9 列为过道（无座），四角为损坏座，5/6 排的 6-7 号为情侣座。

**`seat_index` 预计算规则**（生成阶段一次算准，这是 Bitmap 的地基，算错全盘皆错）：
```
按 row 升序、col 升序遍历
  → 跳过 aisleCols 中的列、跳过 brokenSeats
  → 依次分配连续的 0, 1, 2, 3 ...
seat_id   = "{row}_{col}"  字符串，保证业务可读（如 "5_7"）
seat_index = 连续整数，直接作为 Redis Bitmap 的 offset
seat_type = 0普通 / 1情侣 / 2无障碍
```

**场次生成规则**：
- 日期范围：`CURDATE()` 起未来 7 天
- 每日时段：10:00 / 13:00 / 16:00 / 19:00 / 21:30
- 价格：普通厅 35-55 元，3D 45-65 元，IMAX 75-95 元，按影片热度 + 时段浮动
- 每场 `total_seat` = 该厅有效座位数（总数 - 过道 - 损坏座）
- `t_movie_schedule_seat` 按场次批量 INSERT，每批 1000 行
- 同时灌入部分"已售"座位（随机 20-40%），让座位图看起来真实
- **指定 1 个场次为抢购场次**（`rush_mode=1`，仅 200 个座位，`rush_start_time` 设为未来时刻），用于压测百万级抢票场景

**重置脚本**：`docs/sql/reset_demo.sql` 清空并重建演示数据，方便反复压测。

## 六、核心接口清单

### gateway 路由约定
`/api/{service}/**` → 去掉 `/api` 前缀转发到对应服务。JWT 校验通过后，把 `X-User-Id` 写入请求头透传给下游。

### user-service
| 方法 | 路径 | 说明 | 鉴权 |
|---|---|---|---|
| POST | `/user/register` | 手机号注册 | 否 |
| POST | `/user/login` | 登录，返回 JWT | 否 |
| POST | `/user/logout` | 登出，JWT 写入 Redis 黑名单 | 是 |
| GET | `/user/info` | 当前用户信息 | 是 |
| GET | `/user/coupon/available` | 可用优惠券列表（按金额） | 是 |
| POST | `/inner/coupon/lock` | **内部**：锁定优惠券（Seata 分支） | 内部 |

### movie-service
| 方法 | 路径 | 说明 | 鉴权 |
|---|---|---|---|
| GET | `/movie/film/list` | 影片列表（按状态筛选） | 否 |
| GET | `/movie/film/{id}` | 影片详情 | 否 |
| GET | `/movie/cinema/list` | 影院列表（按影片+日期筛有排片的影院） | 否 |
| GET | `/movie/schedule/list` | 某影院某影片某日的场次列表 | 否 |
| GET | `/movie/schedule/{id}` | 场次详情（含余票） | 否 |
| POST | `/inner/schedule/occupy` | **内部**：锁场次库存 + 座位行 0→1（Seata 分支 G1） | 内部 |
| POST | `/inner/schedule/sold` | **内部**：座位行 1→2 出票（Seata 分支 G2） | 内部 |
| POST | `/inner/schedule/release` | **内部**：座位行 2→0 释放（Seata 分支 G3） | 内部 |

### seat-service

## 七、选座与百万级抢票方案（项目核心）

### 7.1 Key 设计

| Key | 类型 | 说明 |
|---|---|---|
| `seat:map:{scheduleId}` | Bitmap | 第 N 位 = 该场次 seat_index=N 的座位是否被占（1=锁或售） |
| `seat:owner:{scheduleId}` | Hash | field=seatIndex, value=`{orderNo}` 或 `SOLD:{orderNo}` |
| `seat:delay:{scheduleId}` | ZSet | member=orderNo, score=锁过期时间戳（毫秒），用于超时扫描 |
| `seat:order:{orderNo}` | Set | 该订单占用的所有 seatIndex，供释放时批量读取 |

**Bitmap 只回答"能否选"，owner Hash 回答"谁占的"**——两者职责分离，释放操作靠 owner 校验防止误清他人座位。

### 7.2 seat_lock.lua（防超卖的唯一仲裁点）

```lua
-- KEYS[1] = seat:map:{scheduleId}
-- KEYS[2] = seat:owner:{scheduleId}
-- KEYS[3] = seat:delay:{scheduleId}
-- KEYS[4] = seat:order:{orderNo}
-- ARGV[1] = orderNo
-- ARGV[2] = expireTs (毫秒时间戳)
-- ARGV[3..] = seatIndex 列表
local mapKey, ownerKey, delayKey, orderKey = KEYS[1], KEYS[2], KEYS[3], KEYS[4]
local orderNo  = ARGV[1]
local expireTs = tonumber(ARGV[2])

-- 第一轮：全量校验，任一不可选则整体失败（不产生部分占位）
for i = 3, #ARGV do
    local seatIndex = tonumber(ARGV[i])
    if redis.call('GETBIT', mapKey, seatIndex) == 1 then
        return {0, seatIndex}          -- 返回冲突座位，前端高亮提示
    end
end

-- 第二轮：批量占位。校验与占位之间无任何其他命令，
-- Redis 单线程执行 Lua 保证这段逻辑与外界的原子性。
for i = 3, #ARGV do
    local seatIndex = tonumber(ARGV[i])
    redis.call('SETBIT', mapKey, seatIndex, 1)
    redis.call('HSET',   ownerKey, seatIndex, orderNo)
    redis.call('SADD',   orderKey, seatIndex)
end
redis.call('EXPIRE', orderKey, 7200)   -- 兜底 TTL，防订单异常残留
redis.call('ZADD',   delayKey, expireTs, orderNo)
return {1, #ARGV - 2}
```

### 7.3 seat_release.lua（带 owner 校验的幂等释放）

```lua
-- KEYS[1..4] 同上，ARGV[1]=orderNo，ARGV[2]='1' 表示强制释放（仅对账修复用）
local seats = redis.call('SMEMBERS', KEYS[4])
local orderNo, force, released = ARGV[1], ARGV[2] == '1', 0
for _, s in ipairs(seats) do
    local idx   = tonumber(s)
    local owner = redis.call('HGET', KEYS[2], idx)
    -- 只释放仍属于本订单的座位，防止补偿任务误清已被他人买走的座位
    if owner == orderNo or (force and not owner) then
        redis.call('SETBIT', KEYS[1], idx, 0)
        redis.call('HDEL',   KEYS[2], idx)
        released = released + 1
    end
end
redis.call('DEL',  KEYS[4])
redis.call('ZREM', KEYS[3], orderNo)
return released
```

### 7.4 seat_confirm.lua（支付成功，锁 → 售出）

```lua
-- 语义：不清 bitmap（保持 1 = 已售），只摘掉"待超时释放"的标记
local seats = redis.call('SMEMBERS', KEYS[3])
for _, s in ipairs(seats) do
    redis.call('HSET', KEYS[1], tonumber(s), 'SOLD:' .. ARGV[1])
end
redis.call('ZREM', KEYS[2], ARGV[1])          -- 不再参与超时扫描
redis.call('EXPIRE', KEYS[3], 604800)         -- 保留 7 天供对账
return 1
```

### 7.5 锁超时释放（双通道）

- **主通道**：下单成功即发 RocketMQ 延迟消息（15 min），消费后执行 `seat_release.lua`
- **兜底通道**：`@Scheduled` 每 30s 扫 `ZRANGEBYSCORE seat:delay:{sid} 0 {now} LIMIT 0 100`，逐个释放
- **不允许只靠定时扫描**（最长 1 分钟延迟体验差），**也不允许只靠 MQ**（消费失败重试期间需兜底）

### 7.6 Redis 与 MySQL 的最终一致性

| 时机 | 动作 |
|---|---|
| 锁座成功 | 只写 Redis，**不写 DB**（高频操作不碰磁盘） |
| 下单落库 | Seata 分支把座位行写成 `status=1` + `lock_order_no` |
| 支付成功 | 座位行 `1→2`，同时 `seat_confirm.lua` |
| 超时/取消 | 座位行 `1→0`，同时 `seat_release.lua` |
| **对账兜底** | 每 5 分钟扫未来 6h 开场的场次，比对 Redis bit 与 DB `status`，差异时**以 DB 为准修正 Redis**，`status=2 但 bit=0` 的情况额外告警 |

**Redis 挂了怎么办**：锁座接口**直接返回 503 拒绝服务**，不做降级。降级到 DB 行锁抢座会让 MySQL 瞬间被打挂，比拒绝服务更糟。

### 7.7 Bitmap 初始化与重建

- 排片时批量预计算 `seat_index` 落库，Redis 侧不预建 bitmap（首次 `SETBIT` 自动扩展，默认全 0 = 全可选）
- 从 DB 重建：新 key `seat:map:{sid}:rebuild` 灌入后 `RENAME` 替换（Redis 原子命令），避免重建期间的读写错乱

### 7.8 抢购场次的完整链路

```
用户点"立即抢票"
  → gateway 过滤器: 先查 sold_out:{sid} / rush:paused:{sid}
       已售罄 → 直接返回"已售罄"，不进任何后端服务
       已暂停 → 返回"抢购已暂停"
  → queue-service  POST /queue/join
       ZADD queue:wait:{sid} {now} {userId}    （ZSet 天然去重，重复点击无副作用）
       返回 {rank: 12847, status: WAITING}
  → 前端每 2s 轮询 GET /queue/position
       直到 status=PASSED，拿到 ticketToken
  → 用户带 ticketToken 调 POST /seat/lock
       gateway 校验令牌有效性（Feign → queue-service 或直接读 Redis）
  → 进入正常选座下单流程（§7.2 的 Lua 锁座 → §十 的 G1 事务）
```

普通场次（`rush_mode=0`）**不经过这一层**，链路与原来完全一致。

### 7.9 排队 Redis 数据结构（无 DB，全内存）

| Key | 类型 | 说明 |
|---|---|---|
| `queue:wait:{sid}` | ZSet | member=userId, score=入队时间戳。先到先得，`ZADD` 天然幂等去重 |
| `queue:inflight:{sid}` | ZSet | member=userId, score=令牌过期时间戳。统计"已放行未下单"人数 |
| `queue:token:{sid}:{uid}` | String | 抢票令牌，TTL 300s |
| `sold_out:{sid}` | String | 售罄标记，1=已售罄 |
| `rush:paused:{sid}` | String | 熔断开关，1=暂停抢购 |

**不落 DB 的理由**：队列是瞬态数据，开票后几分钟就空了；Redis 挂了排队本来也进行不下去。用 DB 反而是负担。

### 7.10 放行器（queue-service 核心）

```java
@Scheduled(fixedDelay = 200)   // 每 200ms 一轮
public void dispatch() {
    for (Long sid : 所有开启抢购的场次) {
        if (redis.get("sold_out:" + sid) == 1) { 清空队列; 广播售罄; continue; }
        if (redis.get("rush:paused:" + sid) == 1) continue;

        int remain   = 剩余票数（读 Redis 预扣库存）;
        int inFlight = zcard("queue:inflight:" + sid);   // 已放行未下单
        int quota    = (int)(remain * 1.5) - inFlight;   // ★放行系数
        if (quota <= 0) continue;

        List<String> batch = zpopmin("queue:wait:" + sid, quota);
        for (String uid : batch) {
            redis.setex("queue:token:" + sid + ":" + uid, 300, UUID);   // 5 分钟令牌
            redis.zadd("queue:inflight:" + sid, now + 300_000, uid);
        }
    }
}
```

**放行系数 1.5 的由来**：被放行的人不一定都下单（会放弃、会犹豫、会超时），放行量必须略大于剩余票数才能卖完。但也不能太大——放 10 倍的人进来抢 2000 张票，9900 人空手而归，体验极差。1.5 是平衡点。

**令牌过期视为放弃**：`queue:inflight:{sid}` 的 score 是过期时间戳，清理任务扫出过期的直接移除，**不重新排回队列**（避免恶意占位）。想继续抢就重新 `join`，排到队尾。

**为什么用 `ZPOPMIN` 而不是 `ZRANGE` + `ZREM`**：`ZPOPMIN` 是原子弹出，queue-service 多实例并发放行时不会重复放行同一个人。

### 7.11 售罄快速失败（最有效的单点优化）

2000 张票在 100 毫秒内售罄，后面还有 99.8 万人在疯狂重试。**库存归零的瞬间立刻置 `sold_out:{sid}=1`**，此后所有请求在 gateway 过滤器层就返回"已售罄"，不进 Redis、不进队列、不进任何业务服务。

效果：99.8 万次无效 Redis 请求被压缩成一次布尔判断。Redis 单实例约 10 万 QPS——不做这步，百万 QPS 需要 10 分片集群；做了这步，压力降两个数量级。

**置标记的位置**：在 `seat_lock.lua` 里，库存扣到 0 时顺手 `SET sold_out:{sid} 1`，保证与扣减处于同一原子操作内。

### 7.12 熔断开关

`POST /admin/schedule/{id}/rush/pause` 置 `rush:paused:{sid}=1`，所有入口立即拒绝新请求，已在队列中的人收到"抢购已暂停"通知。

用途：发现异常流量、库存数据错乱、或活动方要求临时中止时一键止血。

## 八、订单状态机

### 8.1 状态定义

| 值 | 状态 | 说明 |
|---|---|---|
| 0 | 待支付 PENDING_PAY | 订单已创建，未发起支付 |
| 1 | 支付中 PAYING | 已创建支付单，等渠道回调 |
| 2 | 已支付 PAID | 支付成功，已出票 |
| 3 | 已完成 COMPLETED | 场次已结束 |
| 4 | 已取消 CANCELLED | 超时未支付 / 用户主动取消 |
| 5 | 退款中 REFUNDING | 已发起退款 |
| 6 | 已退款 REFUNDED | 退款成功 |

### 8.2 流转与守卫条件

| 流转 | 守卫条件 | 触发方 |
|---|---|---|
| 0 → 1 | `status=0 AND lock_expire_time > NOW()` | 创建支付单 |
| 0/1 → 2 | 支付金额匹配 + 渠道交易号唯一 | 支付成功回调（G2） |
| 0 → 4 | `status=0 AND (超时 OR 用户取消)` | 延迟消息 / 用户 |
| 2 → 3 | `status=2 AND 场次已结束 +30min` | 定时任务 |
| 2/3 → 5 | `status IN (2,3) AND 开场时间-now > 2h AND 未验票` | 用户申请退款 |
| 5 → 6 | 渠道退款成功 | 退款回调（G3） |
| 5 → 2 | 退款失败回退 | 退款重试超限 |

### 8.3 并发安全落点

**所有流转必须走统一 CAS，禁止无 WHERE 的 UPDATE**：

```sql
UPDATE t_order_order
SET status = #{toStatus}, update_time = NOW(3)
WHERE order_no = #{orderNo}
  AND status IN (#{fromStatuses});
-- 影响行数 = 1 → 本次流转唯一生效
-- 影响行数 = 0 → 已被其他线程/重复消息处理，直接返回幂等成功
```

这一条 UPDATE 的 `WHERE status IN (...)` 就是订单状态机全部并发安全性的落点。业务代码里**不允许出现无 WHERE 条件的 `UPDATE t_order_order SET status=...`**。所有状态流转集中在 `OrderStateMachine` 单一类中，终态（3/4/6）不可逆的守卫也在此集中。

## 九、支付幂等方案

### 9.1 四层防御

| 层 | 手段 | 拦截场景 |
|---|---|---|
| L1 | `t_pay_notify_log.uk_channel_trade_type` + `INSERT ... ON DUPLICATE KEY UPDATE retry_times+1` | 渠道重复推送（支付宝有 25 次重推机制） |
| L2 | `t_pay_payment` 状态 CAS `WHERE status IN (0,2)` | 并发回调、乱序回调 |
| L3 | `uk_channel_trade(channel, channel_trade_no)` | 同一渠道交易号绑定两个支付单（防伪造/串单） |
| L4 | `t_pay_refund.uk_payment_no` | 重复退款申请 |

**为什么 L1 命中不能直接返回 success**：若首次插入成功但业务处理时进程崩溃，`process_status` 仍为 0；渠道重推时若因唯一索引冲突直接返回 success，这笔支付就永远丢了。所以 L1 只做日志去重，业务幂等必须靠 L2。

### 9.2 支付成功 CAS（乱序防御核心）

```sql
UPDATE t_pay_payment
SET status = 1, channel_trade_no = #{channelTradeNo},
    pay_time = #{channelPayTime}, notify_time = NOW(3), update_time = NOW(3)
WHERE payment_no = #{paymentNo}
  AND status IN (0, 2)          -- 0待支付→正常；2失败→允许被后到的成功回调覆盖
  AND amount = #{notifyAmount}; -- 金额校验，防篡改/串单
```

Java 侧分支：

```java
int rows = paymentMapper.casPaySuccess(...);
if (rows == 0) {
    Payment p = paymentMapper.selectByPaymentNo(paymentNo);
    if (p == null) return FAIL;                                    // 支付单不存在 → 告警
    if (p.getStatus() == 1 && 交易号与金额均匹配) return SUCCESS_IDEMPOTENT;  // 重复回调
    if (p.getStatus() == 1) return FAIL_ALARM;                     // 金额/交易号不符 → 告警
    if (p.getStatus() == 3) return LATE_PAY;                       // 延迟到达，见 9.4
    return FAIL;
}
// rows == 1 → 首次处理成功，继续 G2 出票
```

失败回调单独处理，**绝不覆盖 status=1**：`UPDATE ... SET status=2 WHERE payment_no=? AND status=0`

**并发回调**：两个线程同时 CAS，InnoDB 行锁保证只有一个 `rows=1`，另一个阻塞后拿到 0 走幂等分支。**行锁 + WHERE 条件就是这里唯一的并发边界，不需要分布式锁。**

### 9.3 退款流程与座位释放

**释放时机是核心决策：必须在退款成功后释放，绝不在"申请退款"时释放。**

原因：`REFUNDING`(5) 是中间态，退款可能失败。若申请时就释放座位，座位可能被 B 买走而 A 的退款又失败了 → A 既没票也没退款，B 拿到了票，等于超卖。

| 场景 | 座位处理 | 理由 |
|---|---|---|
| 开场前 > 2h 退款成功 | **释放回池**（bitmap 0 + `schedule_seat 2→0` + `sold_seat -1` + 清 delay） | 时间充裕能再卖，对影院无损，这是猫眼实际行为 |
| 开场前 ≤ 2h | **不允许退款**（接口拒绝） | 电影票特性：临场退票座位卖不掉 |
| 已验票 | **不允许退款** | |
| 场次取消（影院原因） | 全部退款 + 全部释放 | 状态要正确，便于重排 |

**退款单创建幂等**靠 `uk_payment_no` 唯一索引；退款失败按指数退避重试（`retry_count` < 5，超限置 `status=3` + 告警）。

### 9.4 延迟到达（钱到了但支付单已关闭）

最危险场景：15:00 下单 → 15:15 支付单被超时任务关闭 → 15:16 用户付款成功 → 回调到达，CAS 因 `status=3` 不匹配。

**处理原则：钱不能吞。**
1. 识别 `LATE_PAY`，检查订单状态（此时应已 CANCELLED，座位已释放）
2. **自动发起原路退款**，`t_pay_refund.reason='TIME_OUT_PAID'`，`release_seat=0`（座位早已释放，绝不重复释放）
3. 告警通知人工核查
4. 对渠道仍返回 `"success"`（钱已收下且会退回，渠道不该再重推）

**根因缓解**：关闭支付单前先调 `PaymentChannel.query()` 主动查单一次，避免"实际已支付"被误关。这就是 §十一 任务 8 存在的原因。

### 9.5 策略模式抽象

```java
public interface PaymentChannel {
    ChannelType type();                                   // MOCK / ALIPAY
    PrepayResult prepay(PrepayCommand cmd);               // 下单，返回支付链接/二维码
    NotifyResult parseNotify(String rawBody, Map<String,String> headers);  // 验签 + 解析
    QueryResult  query(String paymentNo);                 // 主动查单
    RefundResult refund(RefundCommand cmd);               // 退款

}
```

- `MockPaymentChannel`：调 `mock-pay-gateway`，支持手动触发重复/乱序/失败/验签错误回调
- `AlipaySandboxChannel`：**本期只留骨架**，接沙箱时新增实现类即可，业务代码零改动
- 工厂：`PaymentChannelFactory.get(channelType)`，Spring 注入所有实现

## 十、分布式事务边界

**核心原则：只有"改了会直接影响钱的"才走 Seata AT，通知/统计/清理走 MQ 最终一致。**

### G1 下单（TM: order-service，`@GlobalTransactional`）

```
事务外前置：Redis seat_lock.lua 原子占位（Redis 不参与 Seata，必须在事务边界之外）
           ↓ G1 失败时 catch 补偿执行 seat_release.lua
@GlobalTransactional(name = "create-order", timeoutMills = 30000)
 ① movie-service  POST /inner/schedule/occupy
      UPDATE t_movie_schedule
         SET locked_seat = locked_seat + N
       WHERE id = #{scheduleId} AND status = 1
         AND locked_seat + sold_seat + N <= total_seat;   -- ★防超卖并发边界
      -- 影响行数 ≠ 1 则抛异常回滚

      UPDATE t_movie_schedule_seat
         SET status = 1, lock_order_no = #{orderNo}, lock_user_id = #{userId},
             lock_expire_time = #{expireTime}, version = version + 1
       WHERE schedule_id = #{scheduleId} AND seat_id IN (...)
         AND status = 0;                                   -- ★座位级并发边界
      -- 影响行数 ≠ N 则抛异常回滚
 ② user-service   POST /inner/coupon/lock（有优惠券时才调，同样以影响行数断言）
 ③ order-service  插入 t_order_order + t_order_item
      order_no 唯一索引冲突 → 判定重复提交
```

**顺序很重要**：Redis 锁座 → G1 事务。G1 失败时 Redis 补偿释放是**幂等的**（`seat_release.lua` 校验 owner），重复执行安全。

### G2 出票（TM: pay-service，入口是支付回调）

```
① pay-service   支付单 CAS 0/2 → 1
② order-service UPDATE t_order_order SET status=2, pay_time=? WHERE order_no=? AND status IN (0,1)
③ movie-service UPDATE t_movie_schedule_seat SET status=2, sold_order_no=?, sold_time=NOW(3)
                 WHERE schedule_id=? AND seat_id IN (...) AND status=1
                   AND lock_order_no = #{orderNo};         -- ★必须还是自己锁的
                 UPDATE t_movie_schedule
                    SET sold_seat = sold_seat + N, locked_seat = locked_seat - N
                  WHERE id=? AND locked_seat >= N;
                 同时生成 t_order_item.ticket_no
事务提交后（非事务）：seat_confirm.lua → 发 MQ 通知
```

### G3 退款（TM: pay-service）

```
① pay-service   退款单 CAS → 2
② order-service UPDATE t_order_order SET status=6, refund_time=?, refund_amount=?
                 WHERE order_no=? AND status=5
③ movie-service releaseToPool=1 时：
                 UPDATE t_movie_schedule_seat SET status=0, sold_order_no=NULL
                  WHERE schedule_id=? AND seat_id IN (...) AND status=2 AND sold_order_no=#{orderNo};
                 UPDATE t_movie_schedule SET sold_seat = sold_seat - N WHERE id=? AND sold_seat >= N;
事务提交后：SETBIT 0 释放 Redis 座位（延迟 100ms 无妨）
```

**走 MQ 最终一致的部分**：座位超时释放、订单取消通知、统计埋点、会员成长值、对账差异。凡是可重试、可延迟、不直接影响资金的动作，都不要塞进全局事务——那会把事务时间从 50ms 拉到 500ms，急剧放大锁冲突。

## 十一、定时 / 延迟任务清单

**选型**：`@Scheduled` + **ShedLock**（Redis 实现，多实例互斥）。不引 XXL-Job，多一个组件的运维成本大于收益。

**统一约定**：所有扫描任务分页 + `LIMIT 100~500`，禁止一次性 `SELECT *`。

| # | 任务 | 触发 | 周期 | 扫描条件 | 要点 | 服务 |
|---|---|---|---|---|---|---|
| 1 | 订单超时取消 | **RocketMQ 延迟消息（主）** + 定时（兜底） | 15min / 1min | `status=0 AND lock_expire_time < NOW(3)` | CAS 0→4 → 发 SEAT_RELEASE → 解锁优惠券 | order |
| 2 | 座位锁超时释放 | **RocketMQ 延迟消息（主）** + 定时（兜底） | 15min / 30s | `ZRANGEBYSCORE seat:delay:{sid} 0 now LIMIT 0 100` | `seat_release.lua` | seat |
| 3 | 座位 DB 侧对账释放 | 定时 | 5min | `status=1 AND lock_expire_time < NOW(3)`，只扫未来 6h 场次 | 按 `lock_order_no` 回查订单终态 → 条件更新释放 | movie |
| 4 | Redis↔DB 座位对账 | 定时 | 5min | 未来 6h 场次（限 200 场/轮） | 以 DB 为准修正 Redis；`status=2 但 bit=0` 额外告警 | seat |
| 5 | 场次状态流转 | 定时 | 5min | 按 `start_time` / `end_time` 批量 CAS | 待开售→售票中→放映中→已结束 | movie |
| 6 | 订单自动完成 | 定时 | 5min | `status=2 AND 场次已结束+30min` | CAS 2→3 | order |
| 7 | 支付单超时关闭 | 定时 | 1min | `status=0 AND expire_time < NOW(3)` | **先调 `channel.query()` 主动查单**，确实未支付才 CAS 0→3 | pay |
| 8 | 支付结果主动查询 | 定时 | 2min | `status IN (0,2) AND create_time < NOW()-5min AND > NOW()-2h` | 已成功 → 走 G2；已关闭 → CAS 3 | pay |
| 9 | 退款重试 | 定时 | 1min | `status IN (0,1) AND retry_count < 5 AND next_retry_time <= NOW(3)` | 指数退避 `POW(2, LEAST(retry_count,4))` 分钟 | pay |
| 10 | 回调日志重放 | 定时 | 10min | `process_status=2 AND retry_times < 3 AND create_time > NOW()-1d` | 重新执行业务处理（幂等保证安全） | pay |
| 11 | 日对账 | 定时 | 每天 04:00 | 前一日数据 | 订单 pay_amount 汇总 vs 支付流水 vs 退款；差异落日志 + 告警 | pay |

**任务 1/2 的关系**：同一件事的两个视角（订单侧 / 座位侧），都以 MQ 延迟消息为主触发、定时扫描为兜底。**不允许只依赖定时扫描**（1 分钟延迟体验差），**也不允许只依赖 MQ**（消费失败重试期间需兜底）。

**RocketMQ 5.x 支持任意时刻延迟消息**，无 4.x 的 18 级限制。若降级到 4.x，15min 只能取 10m 或 20m 级别，需改为"延迟 10min + 消费时查 `lock_expire_time` 未到则重发剩余时长"。

## 十二、并发边界汇总（红线清单）

| # | 操作 | 边界 | 保障机制 |
|---|---|---|---|
| 1 | 多座位"校验 + 占位" | 单个 Lua 脚本内，校验与占位之间不可插入 | Redis 单线程执行 Lua |
| 2 | 座位释放（owner 校验 + 清位） | 单个 Lua 脚本内 | 同上 |
| 3 | 场次余量扣减 | 单条 `UPDATE ... WHERE locked+sold+N <= total` | InnoDB 行锁 |
| 4 | 座位行 0→1 占用 | `UPDATE ... WHERE status=0` + 影响行数=N | 行锁 + `uk_schedule_seat` |
| 5 | 座位行 1→2 出票 | `UPDATE ... WHERE status=1 AND lock_order_no=?` | 同上 |
| 6 | 座位行 2→0 退款释放 | `UPDATE ... WHERE status=2 AND sold_order_no=?` | 同上 |
| 7 | 订单任意状态流转 | `UPDATE ... WHERE status IN (from...)` + 影响行数=1 | 行锁 |
| 8 | 支付单成功 CAS | `UPDATE ... WHERE status IN (0,2) AND amount=?` | 行锁 + `uk_channel_trade` |
| 9 | 退款单创建 | `INSERT` 撞 `uk_payment_no` | 唯一索引 |
| 10 | 优惠券锁定/核销 | `UPDATE ... WHERE id=? AND user_id=? AND status=0` | 行锁 |
| 11 | Bitmap 重建 | `RENAME` 替换 key | Redis 原子命令 |
| 12 | 回调去重 | `INSERT ... ON DUPLICATE KEY UPDATE` | 唯一索引 |
| 13 | 排队入队去重 | `ZADD queue:wait:{sid}` | ZSet member 唯一，重复点击无副作用 |
| 14 | 批量放行 | `ZPOPMIN queue:wait:{sid} {quota}` | Redis 原子弹出，多实例不重复放行 |
| 15 | 售罄标记置位 | 并入 `seat_lock.lua` 同一次原子执行 | Redis 单线程执行 Lua |
| 16 | 加入排队 | `ZADD` 前先查 `sold_out` / `rush:paused` | 网关层短路，避免无谓入队 |

**红线反例（禁止）**：先 `GETBIT` 查一遍再 `SETBIT` —— 两步之间会被其他请求插入，必然超卖。这是本方案唯一需要死守的线。

## 十五、已知风险与避坑清单

| 风险 | 表现 | 规避 |
|---|---|---|
| 版本混搭 | Boot 3.4.x 配 SCA 2023.x 启动失败 | 严格按 §1.1 版本矩阵 |
| Seata 依赖冲突 | 启动报 starter 版本冲突 | 引 `spring-cloud-starter-alibaba-seata` 时排除内置 starter，单独引 2.2.0；不同时引 `seata-all` |
| Seata 事务分组 | `can not get cluster name in registry config` | `tx-service-group` 必须与 Server 端 `service.vgroupMapping.xxx` 完全一致 |
| Seata 注册中心不一致 | 发现不了 TC | 客户端与 Server 的 Nacos group/namespace/账号必须一致 |
| Redis 与 DB 座位不一致 | 用户看到可选但实际已售 | §十一 任务 4 对账兜底，以 DB 为准 |
| Nacos 2.x gRPC 端口 | 容器内需同时映射 8848 和 9848 | docker-compose 两个端口都暴露 |
| 座位图渲染卡顿 | 300+ 座位页面卡死 | Canvas 2D 渲染，只重绘变化座位 |
| `unpack` 栈溢出 | Lua 批量 SADD 超 8000 元素崩 | 座位数量可控，超过则分批 SADD |
| Seata 全局锁等待 | 下单高峰锁冲突 | G1 事务控制在 3 个分支内，通知类逻辑一律移出事务 |
| 放行器单点 | queue-service 挂了排队停滞 | 多实例部署，`ZPOPMIN` 原子性保证不重复放行 |
| 排队幻影占位 | 脚本批量 join 占坑等黄牛 | 令牌 5 分钟过期且不重排 + 同 userId 去重；生产环境叠加实名前置 |
| 售罄标记误判 | 提前标记售罄导致票卖不完 | 置位逻辑并入 `seat_lock.lua`，与库存扣减同一原子操作 |
| 抢购场次压垮 Redis | 10 万并发 join 打满单实例 | `ZADD` 是 O(log N)，单实例约 10 万 QPS 可扛；售罄标记让后续请求不落 Redis |

## 十六、设计取舍记录

| 决策 | 选择 | 被否决方案与原因 |
|---|---|---|
| 座位实时状态存哪 | Redis Bitmap 为准，MySQL 为账本 | 纯 DB 行锁：热门场次并发抢座锁等待堆积；纯 Redis 无 DB 兜底：丢数据即超卖 |
| Bitmap offset | 预计算 `seat_index` 落库 | 运行时 `(row-1)*colCount+(col-1)` 反推：无座格位导致 index 不连续，易错 |
| 锁超时释放 | MQ 延迟消息（主）+ 定时扫描（兜底） | 只用 Redis key TTL：key 过期即失忆，无法区分"已售"和"已锁"，DB 侧无法联动 |
| Redis 挂了的降级 | 拒绝服务 503 | 降到 DB 行锁抢座：MySQL 扛不住，会把整个服务打挂 |
| 退款释放座位时机 | 退款**成功后** | 申请时就释放：退款可能失败，会造成超卖 |
| 订单取消的座位释放 | 发 MQ 异步 | 同步 Feign：seat-service 抖动会拖垮取消接口 |
| Seata 使用范围 | 仅 G1/G2/G3 | 全链路 AT：通知类逻辑把事务从 50ms 拉到 500ms，锁冲突急剧放大 |
| 回调处理 | 同步开 AT（Mock 阶段） | 回调只落库 + MQ：更优但更复杂，接真实支付宝遇回调超时时再改 |
| 定时任务 | `@Scheduled` + ShedLock | XXL-Job：多一个组件，练手项目收益不抵成本 |
| 情侣座 | 当作两个相邻普通座位，`seat_type` 只影响展示与定价 | 一个座位占两列：Bitmap 语义、退票粒度、票码生成全部复杂化，不值得 |
| 排队层放哪 | 独立 `queue-service`，网关前置调用 | 并入 seat-service：抢购流量会打穿到业务服务，失去隔离意义 |
| 排队数据存哪 | 纯 Redis，不落 DB | 落 DB：队列是瞬态数据，开票几分钟即空，DB 反成负担 |
| 放行系数 | 剩余票数 × 1.5 | 1:1：放行的人有放弃/超时，票卖不完；×10：9900 人空手而归，体验崩坏 |
| 令牌过期处理 | 视为放弃，不重排队 | 重排回队首：被恶意占位刷爆；重排回队尾：用户愤怒但简单，选前者更稳 |
| 售罄判定位置 | 网关过滤器短路 | 每请求查 Redis：99.8 万次无效请求打满 Redis |
| 抢购要不要摇号 | 本期仍做排队抢，预留摇号扩展 | 直接摇号：供需比超 100:1 时更公平，但缺少"抢"的工程练习价值 |

### 17.7 面试追问准备（校招高频）

**选座并发**
- 为什么用 Redis Bitmap 而不是数据库行锁？→ 热门场次并发抢座会在 MySQL 产生大量锁等待；Bitmap 内存中 O(1) 定位，单 key 无锁竞争
- Lua 为什么能保证原子性？→ Redis 单线程执行命令，Lua 整体执行，中间不插入其他命令
- 为什么不用 Redisson 分布式锁？→ 分布式锁是"串行化"，10 个座位要 10 次加解锁；Lua 一次原子操作处理全部座位，吞吐高一个数量级
- Bitmap 比 Set 省多少内存？→ 200 座位：Set 存 200 个 Long 约 4KB+；Bitmap 仅 `ceil(200/8)` = **25 字节**

**支付幂等**
- 幂等键怎么选？→ 渠道交易号 + 通知类型建唯一索引；支付单号作业务幂等键
- 延迟到达怎么办？→ 识别 `LATE_PAY` → 自动原路退款 + 告警，**绝不吞钱**

**分布式事务**
- 为什么不全用 Seata？→ 出票要调第三方渠道不可回滚；通知类逻辑塞进事务会把 50ms 拉到 500ms，锁冲突急剧放大
- Seata AT 原理？→ 一阶段拦截 SQL 生成前后镜像写入 `undo_log`，二阶段提交删日志 / 回滚用镜像反向补偿，全局锁防写冲突

**可能延伸到项目之外**
- 项目里哪里会 OOM？怎么排查？→ 大场次 `schedule_seat` 批量查询、导出功能；MAT 分析堆转储
- 线程池怎么配？→ 放行器、MQ 消费者、定时任务各自独立线程池，避免相互阻塞

### 17.8 代码质量基线
- 统一返回体 `R<T>` + 全局异常处理，**Controller 不写 try-catch**
- 分层严格：Controller 只做参数校验与转换，业务逻辑在 Service，**禁止 Controller 直接调 Mapper**
- 关键路径必打日志且带 traceId：下单、锁座、支付回调、状态流转
- 所有 SQL 走 MyBatis-Plus，**禁止字符串拼接**
- 配置外置到 Nacos，敏感信息走环境变量
