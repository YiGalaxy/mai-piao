# 麦票：当前实现与架构

本页描述仓库在 **2026-10-01** 的代码状态。最初的九服务方案、未落地技术和计划中的接口
保存在 [历史规划](历史规划.md)；它是设计过程记录，不能当作当前功能清单。

## 项目边界

麦票是 Java 微服务票务学习项目，覆盖电影和演出。重点是并发选座、订单状态迁移、
跨库事务、支付幂等和抢购入口削峰。真实支付、生产级部署、分库分表和百万并发用户
没有落地。管理后台是前端应用；后端管理接口分布在现有业务服务，**没有独立 admin-service**。

## 一次购票如何完成

1. **入口认证。** Gateway 验证 JWT，剥除客户端自带的身份头，再注入可信的用户 ID。
   `/api/*/admin/**` 需要管理员角色；内部 `inner` 路径不能通过网关公开访问。
2. **抢购准入。** 抢购场次先经过 queue 服务的 Redis ZSet 排队，调度器分批放行；
   gateway 负责入口短路，seat 服务仍独立校验放行凭证。普通场次不走排队。
3. **锁座。** seat 服务按账本预计算的 `seat_index` 操作 Bitmap。Lua 一次检查全部
   候选座位并写入占用；Hash 记录归属，ZSet 记录过期时间。一个座位冲突则整批失败。
4. **下单。** order 服务验证锁座 token，在 Seata G1 事务中占场次库存和座位账本、
   可选地锁优惠券，最后写订单及明细。Redis 不受 Seata 回滚，失败后显式补偿释放。
5. **支付出票。** pay 服务验签并记录回调。成功回调通过支付单 CAS 进入 Seata G2，
   同时更新订单、MySQL 座位账本和票码。事务提交后再尽力把 Redis owner 转成已售。
6. **超时和退款。** 当前由定时扫描取消过期未付订单。退款成功后 Seata G3 变更
   退款单、订单和座位账本，随后释放 Redis 已售占用；失败退款有定时重试。

关键入口可从 `SeatMapService`、`OrderService`、`PaymentService`、`PaymentTxService`、
`AdmissionDispatcher` 和 `JwtAuthFilter` 向下追踪。下单依赖同步 Feign 调用；延迟消息
取消订单目前属于历史方案，不能作为现行主链路讲解。

## 并发与一致性边界

- **Redis 原子性：** Lua 把读和写放在一个脚本中，避免两个请求同时看到空位。
- **数据库兜底：** MySQL 场次座位行按旧状态条件更新；Redis 快速判断，MySQL 记录
  业务归属和售出事实。
- **状态机幂等：** 订单、支付、退款按允许的旧状态 CAS 更新；0 行表示状态已变化，
  不能无条件重试为新状态。
- **支付回调：** 验签、回调日志唯一键、支付单 CAS、渠道交易号唯一键和退款单唯一键
  共同处理重复、乱序及延迟回调。
- **事务范围：** Seata 只覆盖相关数据库分支；Redis、外部支付和通知靠补偿或重试。
- **当前缺口：** 支付后 Redis 标记失败只记录日志；完整自动化对账和可靠补偿任务
  尚未实现，不能声称已具备生产级最终一致性闭环。

## 本地运行

从项目根目录启动 `docker/docker-compose.yml`。MySQL 只在**全新数据卷**上自动执行
`docs/sql/schema/`；随后按文件名顺序导入 `docs/sql/demo/`。启动 8 个后端进程，
再启动两个 Vite 前端（用户端 `5273`、管理端 `5274`）。详细命令见 [README](../README.md)
和 [数据库脚本说明](sql/README.md)。

排片生成接口是开发辅助功能，默认关闭。只有在启动 movie 服务的终端设置
`MAIPIAO_DEMO_ENABLED=true` 才能执行 `/movie/demo/*`；调用 `generate-schedule` 会清除
已有场次，随后再调用 `generate-showcase`。网关会要求管理员 JWT；README 中的
`127.0.0.1:9002` 是**本地直连**示例，绕过网关鉴权，不能对外开放业务服务端口。

## 验证范围

当前 Maven 自动化测试是 `SeatRunsTest` 与 `AdmissionDispatcherTest`，各 7 例，共 14 例。
前端 CI 只构建，未配置测试。Redis Lua、跨库 Seata、支付回调和网关鉴权缺少自动化集成
测试。测试通过只能说明已有单元测试覆盖的逻辑，不能证明完整购票链路。

历史压测和复现脚本见 [压测报告](压测报告.md)。其中 `rush-ladder.sh` 使用模拟 JWT
只调用排队和 `/api/seat/assign`，测到的是**锁座分配**，不是订单、支付或最终售票。
`flood.sh` 事先手动写入售罄标记，测的是网关拒绝路径。不得把这些数字表述为
“10 万人完成支付”或“全链路 2 万 QPS”。
