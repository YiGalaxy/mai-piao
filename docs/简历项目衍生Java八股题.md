# 从项目描述衍生的 Java 八股题

## 主问题

你的项目中多个请求可能同时抢同一座位，为什么不能只用 Java 的 `synchronized` 或 `ReentrantLock`？如果项目部署多个订单/座位服务实例，你会怎样保证并发安全？请说明 JVM 锁、Redis/Lua 和 MySQL 条件更新分别解决什么问题。

## 参考回答

`synchronized` 和 `ReentrantLock` 只能约束同一个 JVM 中、使用同一把锁的线程。如果座位服务部署了两个实例：

```text
实例 A 的 JVM 锁
实例 B 的 JVM 锁
```

A 和 B 仍然可以同时访问同一个 Redis 座位，因此 JVM 锁不能作为微服务集群的最终方案。

项目使用三层保护：

1. **Redis Lua：** 在 Redis 内原子地检查 Bitmap，再设置 Bitmap、owner Hash 和订单座位集合。它解决的是“两个请求同时读到座位空闲，然后都写占用”的 Redis 竞争窗口。
2. **MySQL 条件更新：** 创建订单时检查总库存和具体座位状态；库存条件不满足或座位影响行数不符合预期就回滚。这是持久化层的最终防超卖约束。
3. **业务状态/CAS：** 下单预约、支付、取消和退款都带原状态条件，影响行数为 0 时说明本次没有取得状态迁移权，不能继续执行后续业务。

Redis 分布式锁可以减少重复执行，但它有租期、网络和故障问题，不能替代 MySQL 条件更新和业务幂等。Lua 的原子性也不等于 Redis 与 MySQL 是同一个事务；Redis 更新失败或数据库事务结果未知时，仍需要持久预约状态、XID 查询和补偿任务。

## 追问参考答案

### 1. `synchronized` 和 `ReentrantLock` 有什么区别？

`synchronized` 是 Java 语言级别的内置监视器锁，进入同步块自动获取，退出同步块（包括异常退出）自动释放；`ReentrantLock` 是显式锁，需要 `lock()`/`unlock()`，通常在 `finally` 中释放，并提供可中断获取、超时获取、公平策略和多个 `Condition` 等能力。两者都是 JVM 内的线程同步手段，不能直接协调不同服务实例。

### 2. `volatile` 能不能防止两个请求同时锁座？

不能。`volatile` 保证变量的可见性和一定的有序性，不会把“读取座位状态、判断空闲、设置占用”这几步合成原子操作，也无法协调多 JVM。项目要用 Redis Lua 和 MySQL 条件更新处理这些跨请求、跨实例的竞争。

### 3. Java CAS 和数据库条件更新有什么相似点？

两者都是“只有当前值符合预期才修改”的比较并交换思路。Java CAS 通常是 CPU 原子指令，操作进程内变量；项目中的数据库 CAS 通过 `UPDATE ... WHERE status = expected_status` 修改持久状态，依据影响行数判断是否抢到状态迁移权。两者作用范围和事务语义不同，不能互换。

### 4. ABA 问题是什么？本项目哪里要关注？

一个值从 A 变成 B，再回到 A，CAS 只比较当前值时可能误以为期间没有变化。对内存 CAS，常见做法是带版本号或使用带 stamp 的引用。项目的数据库业务迁移有明确状态序列，并在预约 claim 中同时写入 XID、请求摘要并限定来源状态；完成预约时再匹配 token、PROCESSING 和原 XID，避免旧事务结果覆盖新尝试。对于库存计数或 seat owner，不应只根据“现在看起来和原来相同”推断从未变化。

### 5. Redis Lua 为什么能用于锁座？它的原子性边界是什么？

Redis 在执行 Lua 脚本期间不会穿插执行其他客户端命令，因此检查 Bitmap 后再写 Bitmap/owner 的步骤不会被另一个 Redis 请求插入。原子性只覆盖 Redis 脚本的执行，不包括 MySQL、HTTP、Seata 全局事务或支付渠道。Lua 脚本也不是数据库事务：运行时错误不应被理解为所有前面写入必然自动撤销，因此脚本要控制参数和命令错误，并配合账本核验与恢复。

### 6. Redis 分布式锁为什么不能作为唯一正确性保证？

锁可能因租期过期、进程暂停、网络分区、主从切换或误删而失效；旧持有者恢复后，可能和新持有者同时继续执行。分布式锁适合减少重复工作，但关键写入仍需数据库状态条件、唯一约束、owner 检查和幂等操作保护。ShedLock 也只是调度任务的协调手段。

### 7. 两个请求同时执行 `UPDATE ... WHERE status = 0` 会怎样？

两个请求竞争同一行时，InnoDB 会协调行级修改。第一个满足 `status = 0` 的更新把状态改走；另一个随后检查条件时不再匹配，影响行数为 0。业务代码必须检查影响行数，并将 0 解释为本次没有抢到状态迁移权；不能假设 SQL 影响 0 行会自动抛异常或自动回滚整个业务。

## 其他可从项目经历延伸的 Java 题

### 8. ThreadPoolExecutor 的七个参数是什么？

`corePoolSize` 核心线程数、`maximumPoolSize` 最大线程数、`keepAliveTime` 非核心线程空闲存活时间、`unit` 时间单位、`workQueue` 等待队列、`threadFactory` 线程工厂、`handler` 拒绝策略。对补偿任务应使用有界队列，并明确队列满时如何保留未提交记录；不能让拒绝策略静默丢掉业务任务。

### 9. ThreadPoolExecutor 接到任务后按什么顺序处理？

先创建线程直到核心线程数；达到核心数后优先入队；队列满后再增加线程直到最大线程数；线程数达到最大且队列也满时执行拒绝策略。比如 core=4、max=8、queue=50，且每个任务都没结束，前 4 个任务运行，后 50 个排队，第 55 个起创建额外线程运行，最多 8 个同时运行；第 59 个任务会触发拒绝。

### 10. `@Scheduled` 的 `fixedDelay` 和 `fixedRate` 有什么区别？

`fixedDelay` 从上次执行完成开始计时，再等待给定时长；`fixedRate` 按固定时间间隔安排开始时间。需要避免同一任务重叠或让上一轮完成后再间隔时，常用 `fixedDelay`。项目的座位同步默认结束后等待 10 秒。

### 11. Spring `@Transactional` 是怎么生效的？自调用为什么可能失效？

Spring 通常通过 AOP 代理在方法调用前开启事务、成功后提交、异常时回滚。调用必须经过 Spring 管理的代理对象；同一个对象内部 `this.otherTransactionalMethod()` 属于自调用，通常绕过代理，因此标注的方法可能没有按预期创建事务。项目把 Seata 全局事务边界放在独立的协调器 Bean，并通过 Spring 代理调用，不能把事务逻辑绕过代理。

### 12. `@Transactional(rollbackFor = Exception.class)` 解决什么问题？

Spring 默认通常对 `RuntimeException` 和 `Error` 回滚，受检异常默认不一定触发回滚。指定 `rollbackFor = Exception.class` 可让该方法抛出 Exception 时也触发本地事务回滚。它只作用于该 Spring 事务管理器所管理的本地资源，不会自动回滚 Redis、HTTP 调用或外部渠道；Seata 全局事务还需要相应的全局事务协调。

### 13. Seata 全局事务和 Spring 本地事务有什么区别？

Spring 本地事务负责一个服务内由本地事务管理器管理的数据库事务；Seata 全局事务协调多个服务的数据库分支。AT 模式下分支本地提交后仍可能等待 TC 的全局决议，并借助 undo_log 支持回滚。Redis 和外部支付渠道不因为调用链中存在 `@GlobalTransactional` 就自动加入 AT。

### 14. ThreadLocal 是什么？服务间调用时上下文会自动传递吗？

`ThreadLocal` 是每条 Java 线程独立持有变量的机制，适合在一次线程内保存请求上下文。线程池会复用线程，所以使用后必须清理，避免下个请求读到旧值。不同线程、不同 JVM 之间不会自动共享 ThreadLocal；需要通过消息头、HTTP header 或框架拦截器显式传递。Seata XID 与用户身份的传播机制也要分别确认，不能假设因为本线程有值，远程服务就自动有值。

### 15. 为什么补偿线程池要有界队列？

无界队列在生产速度长期大于消费速度时会持续占用内存，并且 `maximumPoolSize` 通常不会在队列未满时发挥扩容作用。有界队列可以明确系统承载边界；队列满时要通过拒绝策略让调用方知道，并将未提交的补偿记录保留在数据库，供下一轮处理。线程池解决吞吐隔离，不替代持久队列和业务幂等。
