# 压测报告

两个不同的问题，两套工具，两组不能混着看的数字。

**复现**：`docs/loadtest/` 下有两个脚本，都能直接跑。

```bash
./rush-ladder.sh 200 2000 5000 10000 20000   # 排队链路阶梯
./flood.sh 800000 2000                        # 纯流量
```

---

## 一、真实买家走完整排队链路

`rush-ladder.sh` —— 加入队列 → 等待叫号 → 拿令牌 → 买票。测的是**排队体验**，以及
系统在人群下会不会超卖。

2000 座，周杰伦演示场次，跨全部 4 个票档，买家随机选档：

| 买家 | 入队 | 被放行 | 抢到票 | 网关售罄短路 | 超卖 | 耗时 | 购票延迟 | 错误 |
|---|---|---|---|---|---|---|---|---|
| 2,000 | 1,981 | 1,878 | 1,770 | 0 | 0 | 32.1s | 232ms | 19 |
| 5,000 | 2,591 | 2,393 | **2,000** | 2,607 | 0 | 12.0s | 249ms | 0 |
| 10,000 | 2,690 | 2,493 | **2,000** | 7,507 | 0 | 12.8s | 183ms | 0 |
| 20,000 | 2,651 | 2,457 | **2,000** | 17,543 | 0 | 12.2s | 178ms | 0 |
| 50,000 | 2,911 | 2,413 | **2,000** | 47,587 | 0 | 19.5s | 549ms | 0 |
| 100,000 | 3,200 | 2,402 | **2,000** | 97,598 | 0 | 28.2s | 1,128ms | 0 |

**每一轮都恰好卖出 2000 张、落在 2000 个不同座位上，没有任何座位被卖两次。**

### 两处要说明的

**2000 买家那轮只卖了 1770。** 工具让每个买家随机挑票档，某档满了他就被拒，而别的档
还有座 —— 真实售票就是这样，但那轮测的是「票档卖完」而不是「场馆售罄」。19 个错误也
是那一轮的，后五轮全部为 0。

**购票延迟随规模上升**：20k 时 178ms，100k 时 1128ms。这是真实的代价 —— 排队的人越多，
被放行的人等得越久。放行量按**剩余票数**算而不是按队列长度算，否则越卖不出去放得越快，
最后所有人空手而归。

## 二、纯流量（"百万请求"的实际含义）

`flood.sh` —— 场次置为售罄，然后用最大并发猛打 `/api/seat/assign`。跳过所有人的步骤，
问的是**边缘能多快地说不**。

| 请求数 | 并发 | 吞吐 | 售罄拒绝 | 到达座位服务 | 错误 |
|---|---|---|---|---|---|
| 100,000 | 400 | 13,550 req/s | 100,000 | 0 | 0 |
| 200,000 | 800 | 16,861 req/s | 200,000 | 0 | 0 |
| 400,000 | 1,200 | 20,600 req/s | 400,000 | 0 | 0 |
| **800,000** | **2,000** | **22,223 req/s** | 800,000 | 0 | 0 |
| 2 × 300,000 | 2 × 1,000 | 20,570 req/s 合计 | 600,000 | 0 | 52 |

**上限定在约 22,000 req/s，瓶颈在网关。** 两个压测进程并行得到的总吞吐与单进程相同，
所以限制不在压测端。座位服务在整个 150 万请求期间**日志一行没增**，网关**零 ERROR**。

按这个吞吐，一百万请求约需 **45 秒**。

---

## 上限是怎么来的

三个限制，按可提升难度排：

1. **账号池** —— 每个买家需要一个独立 userId，队列靠它去重。目前 12 万，这是最容易提的
2. **机器** —— 32 核，压测期间剩余内存 8.8 GB
3. **网关 22k req/s** —— 真正封顶的一层，最难提

**这是两万买家，不是一百万。** 一台 Windows 机器加九个 JVM 承载不了一百万并发 HTTP
客户端。编一个数字比给出实测的更糟 —— 上面每一行都是跑出来的，原始输出在
`docs/loadtest/rush-2000seats-2026-09-20.txt`。

## 这轮压测查出来的东西

压测不只是拿数字，它查出了三个手测永远不会碰到的 bug：

**1. 冷位图重建会抹掉并发中刚分配的座位。** 座位图的 bitmap 缺失时会从账本重建，
而重建用的是 `RENAME` 覆盖。冷启动时多个请求同时发现 bitmap 不存在，于是各自重建 ——
每一次都把别人刚写下的位一起抹掉。**表现是超卖**：300 买家卖出 271 张票，只落在 240 个
座位上，21 个座位被卖了两次。改成幂等的 `SETBIT` 合并后，同样条件 300 张票落在 300 个
不同座位上、0 重复。

**2. `ZPOPMIN` 在本项目的 Redis 客户端上不可用。** Redisson 解不了那个应答，于是弹出在
服务端发生了、客户端却拿不到结果 —— **排队位置静默消失，没有人被放行**，而表现和
「队列是空的」一模一样。改成 Lua 脚本后恢复正常。

**3. 演出排期会撞场馆同一时刻。** 唯一键在建到一半时失败，留下写了一半的表。现在会记录
已占用的时段并顺延。

三个都不是「性能问题」，是**只有在并发和规模下才显形的正确性问题**。这也是为什么压测
不能只看吞吐 —— 上面那张 0 超卖的表格，是靠先修掉第 1 条才成立的。
