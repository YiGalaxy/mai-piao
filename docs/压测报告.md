# 压测报告

两个不同的问题，两套工具，两组不能混着看的数字。以下将仓库内**可核查的原始
输出**与未随仓库保存原始输出的历史记录分开。`RushSaleTest.java` 只调用排队接口和
`/api/seat/assign`，其中输出字段 `bought` 实际表示**成功锁座**，没有下单或支付。

**复现**：在服务与演示场次已准备好的本地 Bash 环境，进入 `docs/loadtest/`
后运行两个脚本。脚本会重置测试场次或手动标记售罄，不能在有真实业务数据的环境运行。

```bash
./rush-ladder.sh 200 2000 5000 10000 20000   # 排队链路阶梯
./flood.sh 800000 2000                        # 纯流量
```

## 一、模拟用户排队与锁座

`rush-ladder.sh` —— 加入队列 → 等待叫号 → 拿令牌 → 调用选座接口。测的是
**排队与座位分配**，不涉及真实账号、订单或支付。

2000 座，演示场次，跨全部 4 个票档，模拟用户随机选档。下表四轮均可在
`docs/loadtest/rush-2000seats-2026-09-20.txt` 中逐项核对：

| 模拟用户 | 入队 | 被放行 | 成功锁座 | 网关售罄短路 | 重复分配 | 耗时 | 选座延迟 | 错误 |
|---|---|---|---|---|---|---|---|---|
| 2,000 | 1,981 | 1,878 | 1,770 | 0 | 0 | 32.1s | 232ms | 19 |
| 5,000 | 2,591 | 2,393 | **2,000** | 2,607 | 0 | 12.0s | 249ms | 0 |
| 10,000 | 2,690 | 2,493 | **2,000** | 7,507 | 0 | 12.8s | 183ms | 0 |
| 20,000 | 2,651 | 2,457 | **2,000** | 17,543 | 0 | 12.2s | 178ms | 0 |

5,000、10,000、20,000 三轮各有 2,000 次成功锁座，返回的座位下标互不重复；
2,000 人一轮仅成功 1,770 次。原始输出中的 MySQL **已售座位数和订单数均为 0**，
因此本报告不证明最终售票、出票或支付链路无超卖。

### 两处要说明的

**2000 人那轮只锁到 1770。** 工具让每个模拟用户随机挑票档，某档满了他就被拒，而别的档
还有座；那轮测的是「某票档锁满」而不是「场馆锁满」。19 个错误也只出现在那一轮，
后面三轮为 0。

**选座接口延迟**：20,000 人一轮平均约 178ms；这不是下单或支付延迟。放行量按
**剩余座位数**算，而不是按队列长度算。文档早期还记录过 50,000 和 100,000 人轮次，
但仓库没有对应原始输出，这两组数字暂不作为可复核结果。

## 二、纯流量（"百万请求"的实际含义）

`flood.sh` 会**手动向 Redis 写入**售罄标记，然后并发请求 `/api/seat/assign`。
它测的是网关在已售罄条件下的拒绝吞吐，不经过排队、锁座、订单、支付。下面是
旧报告保留的历史数字；仓库未保存这些轮次的原始控制台输出，暂不能独立复核：

| 请求数 | 并发 | 吞吐 | 售罄拒绝 | 到达座位服务 | 错误 |
|---|---|---|---|---|---|
| 100,000 | 400 | 13,550 req/s | 100,000 | 0 | 0 |
| 200,000 | 800 | 16,861 req/s | 200,000 | 0 | 0 |
| 400,000 | 1,200 | 20,600 req/s | 400,000 | 0 | 0 |
| **800,000** | **2,000** | **22,223 req/s** | 800,000 | 0 | 0 |
| 2 × 300,000 | 2 × 1,000 | 20,570 req/s 合计 | 600,000 | 0 | 52 |

旧记录描述单机拒绝路径约 22,000 req/s，不能当作系统完整购票链路的吞吐量。

按旧记录的该路径吞吐量外推，一百万次**已售罄拒绝请求**约需 45 秒；这不是一百万买家完成购票。

## 上限是怎么来的

以下是旧本地测试环境的限制，不能外推为通用系统上限：

1. **模拟身份** —— 压测 Java 程序按连续 userId 自行签发 JWT；它没有在用户库中
   创建真实账号，只能在隔离的开发环境采用这种方式
2. **机器** —— 32 核，压测期间剩余内存 8.8 GB
3. **网关拒绝路径** —— 旧记录约 22k req/s，缺少可复核原始输出

**可核查的最大阶梯是 2 万个模拟身份、200 个并发线程，不是一百万并发用户。**
原始输出在 `docs/loadtest/rush-2000seats-2026-09-20.txt`。

## 这轮压测查出来的东西

压测不只是拿数字，它查出了三个手测永远不会碰到的 bug：

**1. 冷位图重建会抹掉并发中刚分配的座位。** 座位图的 bitmap 缺失时会从账本重建，
而重建用的是 `RENAME` 覆盖。冷启动时多个请求同时发现 bitmap 不存在，于是各自重建 ——
每一次都把别人刚写下的位一起抹掉。历史测试中，300 个模拟用户获得 271 次锁座成功，
但只涉及 240 个座位，其中 21 个座位重复分配。改成幂等的 `SETBIT` 合并后，
同样条件返回 300 个不同座位、0 重复。这里仍然只证明锁座分配阶段。

**2. `ZPOPMIN` 在本项目的 Redis 客户端上不可用。** Redisson 解不了那个应答，于是弹出在
服务端发生了、客户端却拿不到结果 —— **排队位置静默消失，没有人被放行**，而表现和
「队列是空的」一模一样。改成 Lua 脚本后恢复正常。

**3. 演出排期会撞场馆同一时刻。** 唯一键在建到一半时失败，留下写了一半的表。现在会记录
已占用的时段并顺延。

三个都不是「性能问题」，是**只有在并发和规模下才显形的正确性问题**。这也是为什么压测
不能只看吞吐 —— 上面锁座阶段 0 重复分配的表格，是靠先修掉第 1 条才成立的。
