## 1. 目标与范围

在现有项目之外新建独立目录和 Git 仓库，从基础工程、数据结构和用户界面实施麦票。现有项目作为只读参考，实施过程中不覆盖、不清理现有源码；仅迁移经过审查确认有效的业务概念、素材和配置。

麦票项目面向微服务框架和高并发抢票场景的学习与演示，重点验证服务边界、Redis 并发控制、库存一致性、消息处理、故障恢复和可重复部署。项目文档、注释、脚本提示和 Git 提交说明均使用准确、简洁的中文。项目不以生产售票系统认证为目标；若实际部署开放给外部用户，应另行完成安全和运维评审。

麦票的完成标准不是组件都已接入，而是核心购票流程可以从空环境启动，并通过自动化测试证明并发和异常场景下的业务结果正确。

### 执行边界：先完成目标，不扩张范围

- 第一目标是本地可运行、核心购票正确、并发结果可验证；每项技术只在能支撑这些目标时加入。
- 保留微服务学习目标，但先固定最少且有明确边界的服务集合。是否拆分网关、用户、场次/库存、订单、支付由阶段 0 的依赖图和事务边界决定；不得为了“微服务齐全”再拆成无独立数据和职责的小服务。
- 第一版使用本地 Docker Compose 和模拟支付。除非现有技术栈或明确学习目标要求，不加入 Kubernetes、云资源、服务网格、多活、复杂监控平台、真实支付接入和多租户。
- 不为计划本身创建额外框架、通用脚手架或重复文档。能由 Maven/npm/Docker Compose 原生命令完成的工作，不再包一层工具。
- UI 先完成一条真实购票主流程，再扩展页面和视觉细节；不先制作与业务无关的宣传页、动画或大量一次性图片。
- 数据首版只维护基础演示集、边界场景集和参数化并发集三类；不为每个实体和状态各建一份重复数据集。
- 遇到未决技术选型，先记录最多一页的选项、成本和决定，再继续；不得在实现中途无理由更换技术栈。

## 3. 版本控制和提交规则

> **实施优化 12（2026-10-08）—提交单元反映最终依赖。** 阶段 0、1 已独立测试提交。阶段 2—8 的数据库迁移、预留、订单与任务存在共同编译和启动依赖；本轮先完成跨阶段闭环并通过静态、空库、业务、并发、故障和浏览器验收，再按“服务与数据基础”“真实用户/管理界面”“验收与交付文档”三个可审查单元提交。此处明确记录与原先每阶段即时提交的差异，阶段版本以最终验收标签为准；不把未验收代码声明为完成。


每个独立功能依次经过实现、测试、文档更新和差异检查，再创建一个提交。没有通过验收的功能不提交为完成状态。提交尽量保持单一目的；测试和对应实现可放在同一个功能提交中。版本控制只纳入有长期价值、与项目运行或验证直接相关的内容；真实生产数据和无关紧要的文件不纳入版本控制。

提交说明使用中文，标题准确描述变更对象和结果，正文列出主要行为变化及验证方式。建议格式：

```text
<类型>(<范围>): <简明变更>

- <主要行为或原因>
- 验证：<实际执行并通过的测试>
```

类型使用 `feat`、`fix`、`test`、`docs`、`refactor`、`build` 等常见约定，范围使用中文业务名或模块名。示例：

```text
feat(场次): 增加按项目和日期查询场次

- 场次列表按项目和日期过滤
- 验证：场次服务单测和接口集成测试通过
```

默认使用 `main` 分支；较大的独立功能使用短期功能分支，验收后合并。阶段完成后创建中文说明的版本标签。提交前检查 `git status`、差异内容、敏感信息和测试结果。不得将 AI 标记写入作者署名或提交者身份。

数据是可运行项目的一部分，但与业务源码分开维护。仓库中的 `data/` 保存可审查、可重复生成的演示和测试数据定义；`deploy/` 保存数据库容器及空库结构配置；`scripts/database/` 保存检查、迁移、导入和验证脚本。数据库运行后产生的业务数据、日志和本机密钥不提交到 Git。

Git 中的数据边界必须严格区分：只提交可复现的合成数据定义、最小演示样例、生成器、导入脚本和校验清单；真实生产数据、真实用户资料、生产数据库导出、线上日志、运行时数据库文件或业务数据快照一律不提交。压测生成的数据默认写入本地临时目录或数据库，不保存生成结果文件；只有确实需要的最小合成测试夹具才可入库。`.gitignore` 必须覆盖数据库文件和备份、日志、导入临时文件、生成数据输出、个人环境文件和构建产物。

数据集只分为三类，避免相同实体在多份脚本里重复维护；每类有清楚的清单、版本、生成方式、导入顺序和适用测试：

| 数据集 | 覆盖内容 | 使用场景 |
| --- | --- | --- |
| `demo-basic` | 所有核心关系实体的正常样例；含可直接演示的购票链路及必要账号 | 首次启动默认导入 |
| `demo-edge-cases` | 每种实体的关键状态和边界组合，如未开售/售票中/售罄场次、各座位状态、订单/支付/退款状态、优惠券状态 | 首次启动默认导入，用于完整演示和边界测试 |
| `test-concurrency` | 参数化生成的场次、座位、用户和库存；数量由命令参数决定 | 并发测试和压测；绝不随默认启动导入 |

首次初始化导入的 `demo-basic` 与 `demo-edge-cases` 合计不得少于 **200 条业务记录**。这里按成功写入关系数据库业务表的行数统计，包含各实体及其明细；不计系统表、迁移记录、Redis key、日志、文件或压测数据。数据量须分布在矩阵所列的实体类型中，不能用单一实体（例如大量座位）凑数。阶段 0 盘点实际模型后，在数据清单中列出每张业务表的预期条数和合计；`验证数据.ps1` 在首次导入后核对实际数量不少于 200，并逐类检查必需实体和关键状态。

在阶段 0 盘点最终数据模型后，维护一张“实体—状态—样例 ID—测试用例”矩阵。矩阵至少检查：

| 实体类别 | 必须能演示或测试的状态/关系 | 数据来源 |
| --- | --- | --- |
| 用户与权限 | 普通用户、管理员；正常、停用或无权限用例 | 关系数据库数据集 |
| 项目/场馆/影厅/场次 | 项目与场次关联；未开售、售票中、暂停、售罄、取消；不同日期和开场时间 | 关系数据库数据集 |
| 票档/座位/库存 | 至少两个价格档；可选、锁定、已售；库存上限和余量 | 关系数据库数据集；Redis 运行态通过场景脚本生成 |
| 优惠券 | 可用、已锁定、已使用、过期、门槛不满足 | 关系数据库数据集 |
| 订单与明细 | 待支付、已支付、已取消、退款中、已退款；每条明细关联真实座位和场次 | 关系数据库数据集 |
| 支付与通知 | 待支付、成功、失败；重复、乱序、迟到回调用例 | 关系数据库基础记录加模拟渠道场景脚本 |
| 退款 | 处理中、成功、失败/可重试；关联支付和订单 | 关系数据库数据集及故障场景测试 |
| 排队 | 排队中、放行、已消费、过期、暂停、售罄 | Redis 运行态由服务接口/场景脚本生成，不直接导入虚构缓存 |
| 补偿任务/事件 | 待处理、处理中、完成、重试或失败 | 若最终架构有持久化任务表，则由数据集覆盖；否则通过故障注入测试生成 |

“每种类型都能测试和演示”按最终实际实体模型解释：矩阵中的每个实体至少在一种自动化测试中创建或读取，每个关键状态至少有一条断言；无需为不支持的业务状态伪造数据，也不要求每种状态都出现在默认首页。

如某状态只能由真实业务流程产生（例如短期 Redis 准入令牌或延迟队列消息），导入脚本不得伪造不一致的缓存副本；应由配套场景脚本通过服务接口创建，或在数据清单中明确标为运行时生成步骤。

数据生成和导入规范：

- 基础演示数据使用固定种子和稳定 ID，保证截图、接口测试和重复导入结果可复现；较大压测数据通过一个参数化生成器按数量和种子生成，并输出记录数和关系校验报告。避免为少量样例编写独立生成框架。
- 数据集完整覆盖实体类型、关键状态和关联关系，使用外键或等价校验确认用户、订单、订单明细、支付、退款、场次、座位、票档之间没有悬空引用。
- 测试数据仅使用虚构姓名、邮箱、手机号和地址；示例账号密码只用于本地开发，README 明确展示并要求不得用于公网环境。不得复制或脱敏后提交生产数据；本计划默认不需要生产数据。
- 每个数据集在独立事务内导入，并使用导入账本记录数据集版本。已成功导入的相同版本再次执行时明确跳过，不覆盖用户后续修改；导入中途失败时事务回滚该数据集，修复后重跑即可。
- 初始化结构、迁移、基础演示数据、扩展场景数据和压测数据分别执行，禁止将所有数据混入数据库容器启动时的自动 SQL。
- 每个数据集有独立清理或重建说明。破坏性清理脚本必须显式要求确认，并验证目标数据库名称/环境；一键启动与普通导入绝不清空数据库或卷。

提供以下少量脚本，具体使用 PowerShell 以匹配 Windows 本地一键启动，同时保留标准 SQL 或生成器入口；不要为每条 SQL 单独包一层脚本：

```text
scripts/database/
  检查环境.ps1
  初始化数据库.ps1
  导入数据.ps1 -Dataset demo-basic|demo-edge-cases
  生成并发数据.ps1 -Sessions <数量> -SeatsPerSession <数量> -Seed <种子>
  验证数据.ps1
  重建开发数据库.ps1 -ConfirmReset
```

`初始化数据库.ps1` 是克隆仓库后的数据库懒人入口：检查 Docker 和数据库连通性，初始化空库，应用迁移，导入默认 `demo-basic` 与 `demo-edge-cases`，验证业务记录总数不少于 200 且关系完整，最后打印演示账号及并发数据集的生成命令。根目录 `scripts/启动.ps1` 调用数据库初始化，再启动后端和前端；首次数据库初始化失败时停止启动并显示失败步骤。若数据库已有初始化标记，则仅检查迁移和数据状态，不重复覆盖导入。README 必须把 `git clone` 后的第一条命令写成实际存在且验证通过的命令。

分步脚本须能单独执行并支持安全重试。每一步输出开始/成功/失败状态、目标数据库、数据集版本、处理记录数和日志位置；失败时保留足够上下文，不吞错，并指出可重跑的命令。`验证数据.ps1` 检查表结构版本、必要记录数、矩阵中的关键状态覆盖、外键/关联完整性和演示账号可登录。若某个参数不适用于某个脚本，不强行支持 `-WhatIf`；写入型脚本必须提供只读检查/预览方式。危险的清库和重建操作要求 `-ConfirmReset`，并验证 Compose 项目名和数据库名与本地开发配置一致。

## 8. Codex 执行协议

执行本计划时，每个阶段按以下顺序推进，不跳过失败的验收门：

1. 阅读本计划、仓库约定和当前 `git status`；先确认正在操作麦票目录，不在原项目中改业务代码。
2. 将当前阶段拆成可独立验收的小任务；一次只处理一个功能闭环，避免同时铺开多个服务或页面。
3. 开始修改前说明目标文件和验收方式；实现时遵循现有已选技术栈，不引入没有明确收益的新依赖。
4. 功能完成后先运行最窄相关测试，再运行受影响模块的检查；若失败，先修复本功能，不把失败测试留给后续阶段。
5. 更新对应中文文档和数据集清单；检查 `git diff`、密钥、生成物和无关格式变更。
6. 确认测试通过后，使用配置好的真实开发者身份创建中文提交；不得更改身份来伪装其他作者。若身份未配置或不是用户预期身份，停止提交并报告具体配置问题。
7. 提交后检查提交内容和工作区状态，再开始下一个功能。阶段验收通过才进入下一阶段。

遇到阻塞时，先完成不依赖该问题的工作；对于影响数据结构、接口契约或服务边界的分歧，暂停相关实现，给出证据和最小决策点，不自行扩展范围。测试耗时或环境不可用时要如实标记为未验证，不得把静态检查描述成运行验证。
