# 第二轮业务与技术栈优化评估

评估日期：2026-10-24。

范围：当前工作区中的网关、用户、票务、座位、排队、订单、支付服务，以及两个 Vue 前端、SQL、Docker 配置和历史压测代码。包含上一轮尚未提交的预约保留改造。

本文保留初始静态审查时的结论与证据，代码引用及行号对应修改前状态。后续已实施的改造、验证结果与剩余工作见 [第二轮优化实施记录](第二轮优化实施记录.md)，不要将本文的问题清单视为当前代码状态。

## 一、结论与优先级

现有 Java 21、Spring Boot、MySQL、Redis、RocketMQ、Vue 技术方向可以保留。最值得投入的是入口权限、支付退款的一致性、异常恢复和完整交易验证。

上一轮已补充稳定预约 token、固定截止时间、创建资格 CAS、事务结果未知时保留座位、订单权威金额和支付归属校验。这些改造应继续保留，本文的问题是在此基础上的剩余缺口。已有下单路径的 `requireOk` 校验也不能替代其他交易路径的检查。

本文优先级：P0 为应先处理的公开破坏性入口；P1 为交易正确性和关键业务规则；P2 为恢复、性能与工程建设。优先级表示修改顺序，不表示所有风险都经过运行复现。

| 顺序 | 优化项 | 主要影响 |
| --- | --- | --- |
| P0 | 演示数据接口默认开启且落入公开白名单 | 匿名请求可能清理演示场次及其座位、票档 |
| P1 | 支付、退款关键 Feign 写调用未检查业务结果 | 支付记录、订单、出票、库存可能不一致 |
| P1 | 回调日志去重屏蔽后续合法成功通知 | 同一交易先失败后成功时，成功通知可能被跳过 |
| P1 | 支付预创建缺少并发幂等和渠道超时恢复 | 同一订单可能创建多个支付单，出现外部结果未知 |
| P1 | 支付查单、关单及退款最终状态闭环不足 | 回调丢失、超时收款和退款异常难以自动恢复 |
| P1 | 订单退款中与支付退款意图之间存在断点 | 订单停在退款中，但支付服务没有退款记录 |
| P1 | 售票窗口、限购和后台删除规则不完整 | 绕过页面规则，或删除仍有待支付预约的场次 |
| P2 | Redis 恢复、排队入口保护、热点与工程能力 | 故障恢复不完整，性能结论缺少完整交易证据 |

## 二、优先处理的业务与交易问题

### 1. P0：演示数据入口需要默认关闭并要求管理权限

**证据：** `maipiao-gateway/src/main/resources/application.yml:128` 将 `/api/movie/**` 放进白名单；`JwtAuthFilter` 对内部路径、管理路径已有额外保护，但 `/movie/demo` 不属于这两类。`DemoDataController.java:31` 使用 `${maipiao.demo.enabled:true}`，与注释所说的默认不可达相反。

`DemoDataController.java:72` 的清理接口和 `:40` 的生成接口都能调用 `DemoDataService.clearSchedules()`。后者在 `DemoDataService.java:132` 删除 `source=SOURCE_GENERATED` 的场次、座位和票档。因此风险范围是生成的演示场次，并非所有人工场次；演示场次一旦承接订单，同样会影响交易。

**建议：** 默认关闭，限定开发 profile；需要开放时仍放在管理员授权路径，并将公开浏览白名单收窄为具体只读接口。清理工具应拒绝删除已有活跃预约或交易的场次。

**验收：** 匿名和普通用户均无法调用生成、清理；非开发环境不注册或明确禁用这些入口；已有交易数据不被演示重置影响。

### 2. P1：关键跨服务调用必须检查 R 的业务状态

**证据：** `common-web/.../GlobalExceptionHandler.java:45` 将业务异常转换成 HTTP 200 的 `R.fail`。`PaymentTxService.java:60–61` 的订单支付确认、出票和 `:99` 的退款完成调用均忽略 `R`；`OrderRefundService.java:155` 的库存释放也未检查返回结果。未发现统一将这类失败响应转换为异常的 Feign 解码配置。

例如订单拒绝支付状态迁移时，支付服务可能拿到 HTTP 200 后继续出票并将回调记为已处理。`@GlobalTransactional` 不能自动理解返回体里的业务失败。

**建议：** 为关键写调用统一执行 `requireSuccess`，区分重复处理成功、状态冲突和暂时失败。业务失败必须中断后续步骤并让事务感知；对渠道已收款的事实，仍需保留恢复和对账入口。

**验收：** 模拟远端 HTTP 200 + `R.fail`，支付不能继续记录整体成功或继续出票；退款库存释放失败不能被当成完整退款业务已完成。

### 3. P1：回调幂等应围绕业务状态迁移

**证据：** `PaymentService.java:159–175` 按渠道、渠道交易号和 `PAY` 记录通知，若日志 `alreadySucceeded` 则直接返回。`PaymentTxService.java:107` 的失败通知处理返回 true，随后日志被标为处理成功。`NotifyLogService.java:56` 据此跳过后续通知，而 `NotifyLogMapper.java:45` 的键不包含渠道事件 ID 或状态。

同一渠道交易先通知 FAILED、后通知 SUCCESS 时，第二条可能直接被拦截。底层 `PaymentMapper.casPaySuccess` 本来允许状态 2 转 1，但执行不到这一层。

**建议：** 将“这条通知已处理”和“这笔交易已最终成功”分开；有渠道事件 ID 时按事件去重，业务仍使用合法状态 CAS。以本地支付记录确定订单归属，绑定核验渠道、交易号、金额和订单关系；验签通过不代表所有字段关系都已校验。

**验收：** 覆盖 FAILED→SUCCESS、重复 SUCCESS、SUCCESS→FAILED、错误金额与订单关系。重复通知不重复出票，较晚的合法成功也不能被旧失败日志吞掉。

### 4. P1：支付创建需要并发幂等和明确的超时语义

**证据：** `PaymentService.java:86` 先查订单最新支付单，`:109` 再插入新支付单，`:111` 调用渠道预创建；`03_pay.sql` 中 `order_no` 只有普通索引。两个首次并发请求可以都查询不到并生成不同支付单。

此外，本地事务不能回滚外部渠道。渠道创建成功但返回超时、本地事务回滚时，可能留下本地查不到的渠道交易。上一轮的金额与身份检查已经补上，本条针对的是并发和外部副作用。

**建议：** 先持久化支付意图和稳定请求号，再由 CAS 获得渠道调用资格；渠道使用同一业务键幂等创建。超时进入待确认，通过查单恢复。若允许失败后的多次支付尝试，明确支付主单与尝试记录的关系，不能只给订单号加唯一索引就禁止所有后续重试。

**验收：** 并发预创建复用同一有效支付意图；渠道响应丢失后能找回交易；同一订单多笔真实成功时有多收款处理策略。

### 5. P1：补齐支付查单、关单与退款最终确认

**证据：** `PaymentMapper.java:83/93/109` 的关单、过期单查询、待核对查询，及 `NotifyLogMapper.java:74` 的回放查询，目前只发现定义，未发现调用闭环。支付任务主要是已有退款记录的重试。`MockPaymentChannel.query()` 返回 UNKNOWN，`PaymentChannel` 也没有关单和退款查询能力。

当前退款在 `RefundService.java:144–152` 收到 accepted 后直接结清。本地 Mock 定义为立即退款，这在其模拟语义下可以成立；接真实异步渠道时，受理不等于到账，不能只替换 adapter 就认为业务已完成。

**建议：** 为未决支付实现查单、关单及支付成功与订单取消的竞态处理；为退款区分受理、处理中、最终成功、最终失败和结果未知。退款使用稳定退款号，结果未知先查再处理。超时收款退款还要遵守 `releaseSeat=0` 的语义，避免重复释放订单资源。

**验收：** 丢失回调能恢复；关单与成功回调并发有确定结果；订单取消后到账能退款；渠道仅受理时不能展示到账完成；未知资金结果不会触发新的重复退款。

### 6. P1：将退款申请与待发送记录一起持久化

**证据：** `OrderController.java:98` 先完成订单退款状态变更，`:102` 才调用支付退款，并直接取 `getData()`。`OrderRefundService.java:74` 拒绝再次申请 REFUNDING；`RefundService.java:183` 的重试只能看见支付库中已经存在的退款单。

若订单已提交 REFUNDING，但请求尚未到达支付服务就断网或进程退出，支付服务没有可重试记录，用户再次申请也会被拒绝。

**建议：** 在订单本地事务内同时保存固定退款申请号和待发送事件，即 outbox；后台任务重发到支付服务，支付服务按该申请号幂等创建。重复申请返回现有处理结果。可以先用数据库扫描发送，不必为此立即增加新中间件。

**验收：** 在订单状态提交后、支付调用前退出进程，重启后仍可自动继续退款。不能仅在 catch 中将订单还原 PAID，因为渠道是否已收到请求可能未知。

### 7. P1：将售票规则落实到统一后端校验

**证据：** `SeatMapService.java:111–113` 展示 `purchaseLimit/requireRealName/saleStartTime`；`:302` 的自动配座只校验本单数量，未发现自选座的同等限购约束，也未发现按账号或证件累计配额。正常锁座、库存占用路径未见统一的售票起止时间校验。抢购排队已有 `rushStartTime` 判断，不能将其理解为所有购票入口都完成了售票窗口控制。

**建议：** 先定义限购是每单、每账号还是每证件。每单规则覆盖自选座与自动配座；如产品需要人均限购，再实现累计配额预占、支付确认、取消回收。售票窗口由服务端统一校验，并覆盖绕过页面和排队直接调用的情况。

实名购票和验票属于下一阶段业务扩展：当前可见相关字段与退款检查，但未形成购票人绑定、身份验证和检票核销的完整接口链路。若保留“需实名”的产品承诺，就应补上实际校验。

**验收：** 未开售、已停售、超过所定义限额的请求，在所有购买入口得到一致拒绝；并发限购不会超出账号或证件配额；取消回收不重复增加额度。

### 8. P1：后台删场次应与售票状态协同

**证据：** `AdminPerformanceService.java:148–163` 只检查 `soldSeat > 0`，再删除座位、票档和场次。尚未覆盖 lockedSeat、Redis 临时预约和待支付订单，也未先停售并与库存写入完成并发仲裁。

**建议：** 先停售，再核对活跃预约和交易；与库存占用使用可协调的行锁或条件写入。已经承接交易的场次走取消、通知和退款流程。已有更新接口对时间、价格的限制应继续保留。

**验收：** 锁座后未支付的场次不能直接删除；删除与新下单并发不会留下无法兑现的订单。

## 三、恢复能力与高并发优化

### 9. P2：Redis 恢复需要完整状态和恢复闸门

**证据：** `SeatMapService.java:145–197` 以 bitmap 存在判断初始化，随后从数据库播种 bitmap，再单独写 owner。`SeatBitmapService.java:392` 逐个 SETBIT，第一位写入后 key 就存在；`:449` 使用 putAll 写 owner。空账本播种不会创建 bitmap，可能反复回源。

恢复中的请求可能读到半份状态；数据库订单账本也不包含所有尚未下单的临时预约。重建 bitmap 不代表 owner、订单索引、到期集合及活跃场次登记都恢复。这里是静态发现的恢复风险，未在本轮复现超卖。

**建议：** 引入按场次的恢复状态和版本，重建期间暂停该场次新预约；结合订单账本、预约协调记录及事务结果重建并核对完整状态，完成后开放。批量写入并明确标记“空场次已初始化”。未知事务继续保留，不按时间直接释放。

**验收：** 演练 Redis 全丢、仅丢 owner、仅丢订单索引、恢复时并发请求；已售座位不重新开放，临时预约得到正确保留或确认后释放。

### 10. P2：排队入口保护与缓存防击穿

**证据：** `maipiao-queue/.../QueueService.java:370–374` 的时间戳 CAS 不能保证同一场次只有一个回源请求：后续线程可以对最新时间戳继续 CAS 成功，时间窗外也没有互斥；且 gate 是多个场次共用的。元数据失败返回空 map 也需要检查是否放宽业务条件。

排队服务的 ZSET 和入场令牌负责排队、准入；未发现网关完整的接口限流配置。入队、查位置、登录等接口仍需自己的流量保护。`AdmissionDispatcher.java:93–106` 在脚本外读取剩余量和在途量再计算 quota，多实例同时调度时应验证总放行上限。

**建议：** 按场次合并正在执行的元数据加载，例如使用 Caffeine 的原子加载；回源失败短暂退避并明确失败语义。网关补 IP、账号与接口限流，队列设容量，客户端轮询退避；多实例放行使用场次级调度权或在 Lua 中原子核算额度。

**验收：** 冷缓存并发回源数量可控；两个调度实例不会超发准入额度；入队和轮询流量不能压垮入口。准入额度异常不等于必然超卖，数据库库存约束仍须保留。

### 11. P2：先测数据库热点，再决定拆分

`SessionMapper.java:99` 起的占用、确认与释放都会更新同场次计数行；大量不同座位的请求仍可能竞争同一行，Seata AT 还增加全局锁开销。

先测行锁等待、事务时长、Seata 全局锁冲突和连接池等待，再减少事务内往返、批量写入。若证明确为瓶颈，再考虑按场次串行处理或细分计数；保持数据库座位归属和库存条件更新的约束。当前证据不足以要求立即分库分表。

### 12. P2：压测口径应覆盖完整成交

`docs/loadtest/RushSaleTest.java:261/286` 的购买动作调用 `/api/seat/assign`，成功就增加 bought；未包含创建订单、支付、出票。因此 `docs/压测报告.md:30` 的“卖出 2000 张”应改成“成功分配并锁定 2000 个座位”。这仍是有价值的排队、锁座验证。

报告约 22,000 req/s 对应售罄后的拒绝路径，不能作为下单 TPS 或十万人同时成交的证据。

下一轮完整测试应覆盖：入队→锁座→下单→模拟渠道付款→出票→订单和账本核对；分别报告到达速率、同时在途请求、排队等待、p95/p99、成功率、支付出票延迟。加入超时取消、重复回调、服务重启及渠道超时，核对同座位不重复售出、每笔成功支付有票或退款去向等业务不变量。

## 四、技术栈取舍

| 技术/能力 | 当前判断 | 优化方向 |
| --- | --- | --- |
| Java 21 | 保留 | 已足够，优先业务正确性和诊断能力 |
| Spring Boot / Cloud / Alibaba | 保留，成套评估升级 | 当前为 3.2.12 / 2023.0.3 / 2023.0.3.2；按兼容矩阵和回归结果升级，统一依赖管理 |
| MySQL + MyBatis-Plus | 保留 | 条件写入、约束、索引、慢查询和热点事务分析 |
| Redis + Lua | 保留 | 完整恢复、内存与持久化策略、热点监控；普通缓存和交易预约状态需要不同恢复策略 |
| RocketMQ | 保留 | 当前实用场景是订单超时定时消息；没有必要为了技术名词更换 Kafka |
| Seata | 学习分布式可保留 | 配套 TC 恢复、锁冲突监控、未决事务查询和人工裁决；外部支付仍需独立补偿 |
| Spring Scheduled + ShedLock | 当前规模可保留 | 定时任务先保证覆盖、幂等、失败重试和告警；无需立即引入 XXL-JOB |
| Nacos 与微服务划分 | 根据学习目标取舍 | 继续学分布式就补故障闭环；更重业务迭代可逐步收敛服务 |
| Vue 3 + Vite + Pinia + Element Plus | 保留 | ESLint/格式化，少量交易交互测试，逐步引入 TypeScript |
| 数据库变更管理 | 建议引入版本化迁移 | 选 Flyway 或 Liquibase 之一，区分初始化、增量迁移与演示数据 |
| 可观测性 | 建议补齐 | 在现有日志和 traceId 上加入业务指标、任务告警与请求链路关联 |

### 需要特别说明的技术边界

1. **当前 Redis Lua 不能直接迁往 Cluster。** `CommonConstants.java:40–81` 的实际 key 前缀没有场次 hash tag；`SeatBitmapService.java:83–89` 同一脚本包含场次键、订单号键和全局 `seat:active`。若要 Cluster，需要按 `{sessionId}` 重新设计同槽键，并把全局登记从原子脚本中拆出或分片。一个热门场次仍会集中到一个 slot，Cluster 不自动消除单场次热点。
2. **Seata file 模式已有持久目录挂载。** `docker-compose.yml:233` 将 `./data/seata/sessionStore` 挂载到容器，不能说“重建容器必丢事务记录”。它仍是单机文件存储，尚不等于共享存储和高可用；需要 HA 时评估 DB 模式、备份和记录保留策略。前一轮发现的 TC 历史缺失人工核对问题仍然存在。
3. **服务拆分已经存在数据耦合。** seat 服务的 `SeatQueryMapper` 直接读取票务库，movie 服务负责写该库。这是当前实现取舍；若保留微服务，应明确数据所有权和查询契约。个人学习项目不必为了名义上的独立再增加大量远程调用。
4. **不要把 RocketMQ 描述为已经承担整条下单削峰。** 当前订单主要同步执行，MQ 的明确用途是超时处理，并有扫表兜底。若后续改为异步下单，还必须增加持久化受理记录、结果查询、消费幂等和失败补偿。

## 五、工程建设与可选业务扩展

**工程优先项：**

- 将初始化 SQL 与增量迁移分开。现有 `docs/sql/schema` 多处 DROP TABLE 适合初始化，不能用于升级已有业务库；Docker 初始化也不会自动升级已有数据卷。
- 在父 BOM 中统一版本例外并记录原因。例如 Testcontainers 父 BOM 与订单测试中的版本覆盖需要明确管理；支付、安全及前端依赖增加自动扫描。本轮未查询漏洞库，不据此认定具体 CVE 或支持期限。
- 两个前端 package.json 只有 dev/build/preview。先补静态检查及结算页状态恢复、重复提交、超时提示等少量关键测试；逐步迁移 TypeScript。
- 监控长时间 PROCESSING、退款积压、支付账差、待释放座位、MQ 延迟、锁等待及任务最后成功时间；为超过自动恢复边界的记录提供人工核对入口与操作审计。
- 对成功与终态预约制定归档周期；未决事务和未完成释放的记录不能靠普通 TTL 清掉。保留幂等所需身份，避免旧 token 被再次使用。

**业务扩展按产品承诺选择：**

- 电子票核销：服务端原子完成未核销→已核销，记录场次、设备、操作人和时间；重复扫码返回已核销，票号不应独自承担访问授权。
- 实名与人均限购：购票人绑定、证件保护、累计配额和取消回收；没有实际校验前不要只展示“需实名”。
- 退改规则快照：当前开演前两小时的固定规则可用于学习；电影与演唱会若共用系统，应按场次规则生成订单快照，明确整单/部分退、手续费、优惠券和验票后的边界。
- 场次取消与延期：先停止销售，展示处理进度，并通过可靠任务推动退款；与简单删除排期区分流程。

## 六、建议实施顺序

1. **入口与交易正确性：** 关闭演示公开入口，统一关键 Feign 结果校验，修正回调幂等，并补针对性回归。
2. **资金闭环：** 支付创建幂等、查单关单、退款意图可靠投递、退款最终状态确认和异常操作台。
3. **规则与恢复：** 统一售票窗口和限购，限制后台删除，完善 Redis 重建及 TC 未决事务处置。
4. **完整交易验证：** 更正历史压测口径，完成端到端交易及故障演练，根据指标定位热点。
5. **工程与架构：** 版本化迁移、监控和依赖治理；有测量依据后再决定集群化、服务收敛或热点拆分。

对于个人学习与面试，前四步更能证明你理解业务和故障边界。现阶段继续增加 Kafka、Elasticsearch、Kubernetes 等组件，收益低于把现有交易链路补完整。
