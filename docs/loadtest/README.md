# 压测

两个不同的问题，两套工具，两组不能混着看的数字。

## 一、模拟用户排队与锁座

`rush-ladder.sh` —— 加入队列 → 等待叫号 → 拿令牌 → 调用 `/api/seat/assign`。
测的是**排队与锁座分配**，不创建订单，也不触发支付。脚本打印的 `bought` 是历史变量名，
实际表示选座请求成功。

2000 座的演示场次，跨全部 4 个票档，模拟用户随机选档：

| 模拟用户 | 入队 | 被放行 | 成功锁座 | 网关售罄短路 | 重复分配 | 耗时 | 选座延迟 | 错误 |
|---|---|---|---|---|---|---|---|---|
| 2,000 | 1,981 | 1,878 | 1,770 | 0 | 0 | 32.1s | 232ms | 19 |
| 5,000 | 2,591 | 2,393 | **2,000** | 2,607 | 0 | 12.0s | 249ms | 0 |
| 10,000 | 2,690 | 2,493 | **2,000** | 7,507 | 0 | 12.8s | 183ms | 0 |
| 20,000 | 2,651 | 2,457 | **2,000** | 17,543 | 0 | 12.2s | 178ms | 0 |

可核查的原始文件 `rush-2000seats-2026-09-20.txt` 只覆盖以上四轮。
5,000—20,000 人三轮各锁到 2,000 个不同座位；2,000 人那轮只锁到 1,770 个。
原始文件里的订单数和 MySQL 已售座位数都是 **0**，所以不能称为“售出 2,000 张票”。

两处要说明：

- **2000 人那轮只锁到 1770。** 工具让每个模拟用户随机挑票档，某档满了他就被拒，
  而别的档还有座；那轮测的是「某票档锁满」而不是「场馆锁满」。
  19 个错误只出现在那一轮，后面三轮为 0。
- **选座延迟**：20k 一轮约 178ms；这不是支付或出票延迟。旧报告还提及 50k/100k
  两轮，但仓库没有对应原始输出，暂不作为可复核结果。

## 二、纯流量（"百万请求"）

`flood.sh` —— **手动写入 Redis 售罄标记**，然后并发请求 `/api/seat/assign`。
测的是网关的已售罄拒绝路径，不经过真实排队、下单或支付。下表是历史文档数字；
仓库没有保存这些轮次的原始输出，不能独立复核。

| 请求数 | 并发 | 吞吐 | 售罄拒绝 | 到达座位服务 | 错误 |
|---|---|---|---|---|---|
| 100,000 | 400 | 13,550 req/s | 100,000 | 0 | 0 |
| 200,000 | 800 | 16,861 req/s | 200,000 | 0 | 0 |
| 400,000 | 1,200 | 20,600 req/s | 400,000 | 0 | 0 |
| 800,000 | 2,000 | **22,223 req/s** | 800,000 | 0 | 0 |
| 2 × 300,000 | 2 × 1,000 | **20,570 req/s 合计** | 600,000 | 0 | 52 |

旧记录约 22,000 req/s 是**拒绝路径**吞吐，不是完整购票系统吞吐。

按该历史记录外推，一百万次已售罄拒绝请求约需 45 秒。

## 怎么复现

在已启动全套服务并生成演示场次的本地 Bash 环境，进入本目录后运行。
`run-rush.sh` 会重置指定场次的测试状态，`flood.sh` 会手动设置 Redis 售罄标记；
不要在有真实业务数据的环境执行。

```bash
./rush-ladder.sh 200 2000 5000 10000 20000   # 排队链路阶梯
./flood.sh 800000 2000                        # 纯流量
```

`RushSaleTest.java` 为每个模拟用户使用不同的连续 userId，自行签发与本地网关密钥
一致的 JWT；**没有**在用户库创建真实账号，`docs/sql/demo/` 也没有批量账号脚本。
仅能在隔离的本地开发环境运行，不应把压测签名密钥带到真实部署。

## 上限是怎么来的

- **模拟身份。** Java 程序可生成不同 userId，限制更多来自本机资源和业务服务。
- **网关拒绝路径。** 旧记录约 22k req/s，缺少原始输出验证。
- 机器本身：32 核，压测期间剩余内存 8.8 GB。

这些数字只描述旧本地机器和网关拒绝路径，不能外推到完整售票链路。
