# 项目亮点与简历描述

本文根据 2026-10-24 当前工作区源码整理。项目定位为个人学习项目，以下表述描述已实现的代码机制；源码实现、环境部署和容量验证是不同阶段。

## 1. 可直接使用的简历版本

**仿猫眼票务平台｜个人项目｜后端开发**

**项目介绍：** 面向电影及演出场次的票务系统，支持自选座、票档分配、抢购排队、订单支付、超时取消及退款。主要负责后端业务设计与实现，前端通过 AI 辅助开发。

**核心工作与亮点：**

- **并发锁座与防超卖：** 基于 Redis Bitmap 与 Lua 实现多座位原子校验、占用及连座分配，结合 MySQL 库存条件更新、座位状态和订单归属校验，构建总量与单座两层防超卖保护；抢购场景通过 Redis ZSet 排队及一次性资格消费控制准入。
- **下单幂等与异常恢复：** 设计持久预约状态机，以锁座 token 作为稳定订单号，通过 CAS 控制同一预约的下单执行权，并使用 Seata 协调库存、座位账本、优惠券及订单；对结果未知的事务保留预约，通过 XID 查询与恢复任务核对结果，避免超时后重复执行或误释放座位。
- **超时取消与资源回收：** 使用 RocketMQ 定时消息触发未支付订单检查，结合定时扫表补漏；通过支付、取消的状态条件和事务协调，以及座位归属校验，实现重复触发下的幂等回收，并通过持久同步标记及补偿任务处理支付后 Redis 更新失败。
- **管理员操作审计：** 基于自定义 `@AdminAuditLog` 注解和 Spring AOP，在有本地业务库的管理员写操作边界统一记录操作人、资源、请求参数、执行结果和耗时，并对密码、Token 等敏感字段脱敏；审计写入失败只告警，不阻断主业务。

如果简历只留一个文段，可使用：

> 主要负责票务平台后端核心链路，基于 Redis ZSet 实现抢购排队准入，使用 Bitmap 与 Lua 原子锁座，并结合 MySQL 库存及座位状态条件更新防止超卖；设计持久预约状态机，通过稳定订单号、CAS 和 Seata 处理重复下单与事务结果未知；采用 RocketMQ 定时消息与扫表任务处理超时订单，结合归属校验及补偿任务完成座位回收和支付后同步。

技术栈一栏可列核心相关项：Java、Spring Boot、MySQL、Redis、Lua、RocketMQ、Seata。版本和其他组件以项目实际配置及本人掌握情况为准。

## 3. 面试时怎样展开

先用约一分钟讲清楚一条成功链路：排队拿资格 → 原子占座 → 持久预约 → 创建订单 → 支付出票。再选择一个异常场景展开，推荐从“下单响应超时，但后台其实已经成功”开始。

不要只背组件名称。每个亮点至少能回答这三个问题：业务会在哪个并发窗口出错；哪条 Lua、SQL 或状态条件决定谁能成功；执行失败或结果未知后，哪项持久信息能支持恢复。

## 4. 使用这些描述时的边界

- 项目没有通过 RocketMQ 接收所有抢票请求并异步建单，当前 RocketMQ 的核心用途是订单超时触发。
- 数据库分支由 Seata 协调；Redis 更新和外部支付渠道不自动加入同一原子事务，需要结果核验和补偿。
- 当前仍需完善支付中订单的完整查单、关单和取消协议，以及 Redis 整体丢失后的完整预约恢复。
- 历史约 22k req/s 来自售罄拒绝路径，不能作为成交吞吐；完整交易容量需要单独压测。
- 简历中的“设计与实现”需要本人能结合代码说明。AI 辅助完成的部分也应能解释关键选择、正确性依据与局限。
