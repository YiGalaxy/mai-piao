# 第二轮项目面试总结

## 1. 面试范围

本轮围绕简历中的三条项目亮点展开：

1. Redis ZSet 排队、一次性准入、Bitmap/Lua 锁座与 MySQL 双层防超卖。
2. 持久预约状态机、稳定 lockToken、CAS、Seata、XID 和未决事务恢复。
3. RocketMQ 定时消息、定时扫表、支付与取消竞争、退款幂等和支付后 Redis 补偿。

另外追问了 Spring `@Scheduled`、ShedLock、服务实例线程池和 Redis/MySQL 的职责边界。

## 2. 面试表现

### 已经具备的基础

- 能理解 Redis 不能替代 MySQL，知道数据库需要做最终核验。
- 能理解带原状态条件的 SQL 用来处理并发状态竞争。
- 能识别取消与支付同时发生时可能产生迟到支付、重复退款和错误释放座位的问题。
- 能理解幂等的核心定义：同一操作重复执行，最终业务结果不变。
- 能主动质疑“失败立即释放座位”会导致用户丢座，并接受保留原预约重试的设计。
- 能理解 RocketMQ 延时消息解决及时性，定时扫描解决漏消息和故障兜底。

### 当前主要短板

1. **容易只说组件名。** 说“Redis、队列、限流”后，不能马上说明每个组件保护哪一层。应明确：ZSet 管排队顺序，准入 token 控制进入锁座的人数，Lua 防止 Redis 检查与写入之间的竞争，MySQL 条件更新承担最终防超卖。
2. **没有形成完整调用链。** 需要能从“用户排队”讲到“消费准入 token、Redis 锁座、预约持久化、CAS 抢执行权、Seata 创建订单、支付、取消或退款”。
3. **幂等和原子性容易混淆。** Lua 原子性表示脚本内命令不会被插入；幂等性表示重复执行最终业务结果不变。唯一索引、CAS、固定状态写入分别解决不同问题。
4. **Java/Lua/MySQL 边界不清。** Lua 只改 Redis，不会把数据自动写到 MySQL；MySQL 通过库存、座位状态和订单归属条件更新做最终校验。
5. **未决事务的处理还不熟。** 不能把 HTTP 超时当成事务失败，也不能只因为查到订单行就判断全局提交。必须说明 `PROCESSING + XID`、TC 查询、明确提交、明确回滚和结果未知时的动作。
6. **定时任务与分布式锁的作用容易混淆。** `@Scheduled` 负责触发，ShedLock 主要减少多个扫描实例重复执行；它不协调 RocketMQ 消费者，也不能代替订单状态 CAS 和资源释放幂等。
7. **当前实现和后续优化容易混在一起。** 例如当前座位确认脚本还没有完整 owner 冲突返回和确认数量校验；当前补偿也没有完整的失败分类和人工审核状态。面试时应主动说“当前代码的边界”。
8. **对队列链路需要继续熟悉。** 要能说明 ZSet 的 score、调度额度、准入 token TTL、原子消费，以及 token、lockToken、XID 三者的区别。

## 3. 面试结论

目前可以较好地介绍项目的业务目标和技术组件，也能在提示后理解核心设计。但面对连续深挖时，回答还停留在“知道用了什么”，不能稳定地解释“哪一步决定成功、失败后依据什么恢复”。按 Java 后端实习生的项目深挖标准，项目经历具备继续使用的基础，技术细节需要通过源码和故障场景练习补齐。

这不代表项目没有亮点。项目真正有价值的地方是把票务场景拆成了多个正确性问题：高并发入口、单座竞争、数据库最终防超卖、重复下单、支付与取消竞态、跨服务事务结果未知和资源补偿。简历上可以写这些设计，但面试时必须能说明边界，不能把学习项目描述成已经验证过的大规模生产系统。

## 4. 下次面试前的准备顺序

### 第一阶段：背熟一条完整链路

```text
抢购用户进入 ZSet
 -> 调度器按余票发准入 token
 -> 消费 token
 -> Lua 原子锁座
 -> 持久预约 RESERVED
 -> 同 token CAS 抢 PROCESSING
 -> Seata 协调 MySQL 库存、座位账本、优惠券和订单
 -> 明确提交后支付
 -> RocketMQ/扫表取消未支付订单
 -> 支付后 Redis 同步失败由 seat_synced 补偿
```

### 第二阶段：熟记四个决定性条件

```sql
库存：locked_seat + sold_seat + count <= total_seat
锁座：座位 status = 0
出票：座位 status = 1 AND lock_order_no = 当前订单
取消：订单 status = PENDING_PAY
```

### 第三阶段：练五个故障场景

1. Redis 锁座成功，MySQL 下单影响行数为 0。
2. 下单请求超时，但后台可能已经提交。
3. Seata XID 结果未知，预约是否能释放。
4. RocketMQ 消息和定时扫描同时取消订单。
5. 取消先成功后收到支付回调。

每题都用“场景 → 决定成功的 SQL/Lua → 持久状态 → 恢复动作 → 边界”回答。

### 第四阶段：只在读懂后再使用这些表述

- 不要说 Lua 会写 MySQL。
- 不要说 ShedLock 能保证 MQ 和扫描绝不重复。
- 不要说 Seata 会自动回滚 Redis。
- 不要说查询到订单行就等于全局事务成功。
- 不要说当前代码已经完整处理 Redis 丢失、支付中订单查单和所有补偿异常。
- 不要把历史售罄拒绝路径的压测数据当作完整购票成交吞吐。

## 5. 面试开场推荐回答

> 这是一个个人学习用的仿猫眼票务平台，我主要负责后端，前端借助 AI 开发。项目核心链路是抢购排队、锁座、创建订单、支付和超时取消。抢购入口使用 Redis ZSet 排队和一次性准入 token，座位层使用 Bitmap 与 Lua 原子校验和占用，订单创建时再通过 MySQL 库存、座位状态和订单归属条件更新做最终防超卖。针对重复下单和请求结果未知，我用持久预约状态、稳定 lockToken、CAS 和 Seata XID 查询恢复；订单超时使用 RocketMQ 定时消息加定时扫描兜底，支付与取消通过状态条件和退款单幂等处理。项目是学习项目，完整交易容量和部分异常恢复仍需要继续压测和完善。
