# 设计取舍

这份文档记录每个关键决策**否定了什么、为什么**。面试里能被追问 30 分钟的，是这些，
而不是「用了什么技术」。

---

## 座位并发

### 实时状态存哪：Redis Bitmap 为准，MySQL 为账本

**否决：纯数据库行锁。** 热门场次几十人抢同一排，会在 MySQL 上堆起大量锁等待，
把整个库拖慢 —— 而不只是慢这一个场次。

**否决：纯 Redis 不落库。** 丢一次数据就是超卖，没有兜底。

**现状**：Redis 决定「能不能选」，MySQL 决定「归谁」。两者不一致时**以账本为准**修正
Redis，且 `status=2 但 bit=0` 这种方向额外告警。

### 为什么是 Lua 而不是分布式锁

分布式锁是把并发**串行化** —— 买 10 个座位要加解锁 10 次。Lua 一次原子操作处理全部
座位，吞吐高一个数量级。而且 Redis 单线程执行脚本，检查与写入之间插不进任何命令。

**这条是整个方案唯一需要死守的线**：先 `GETBIT` 查一遍再 `SETBIT`，两步之间会被其他
请求插入，必然超卖。

### Bitmap 的 offset 预计算落库

**否决：运行时用 `(row-1) * colCount + (col-1)` 反推。** 一旦场馆有过道列或损坏座，
`seat_index` 就不连续，这个公式直接算错；而且它强依赖 `colCount` 的一致性。

## 连座分配

### 相邻判定用行列几何，不用索引加减

这是本项目里最容易写错、且错了不明显的一处。

剧场过道会在**列号**上留出空档：某场馆第 1 行可用列是 `2,3,4,6,7,8,...`，第 5 列是
走道。于是 `seat_index` 2 是第 4 列、`seat_index` 3 是第 6 列 —— **编号上挨着，房间里
隔着一条通道**。

如果按「索引加一」判相邻，在没有过道的场馆上结果完全正确，到了有走道的场馆就会把两人
分到走道两边。所以 run 只要遇到**索引跳变或列跳变**任一情况就断开。

### 责任划分：Java 算几何，Lua 保原子

Lua 不擅长遍历几何，Java 不擅长原子。

关键性质：**Lua 绝不信任 Java 传来的候选段**，自己逐位重新校验。因为候选来自一次
bitmap 读取，脚本跑到时那次读取早已过期。候选只用来缩小搜索范围，不构成授权。

### 找不到连座时严格失败，不偷偷拆开

连座是对买家的承诺。拆开卖是买家**自己**该做的选择，所以失败时返回
`{0, longestFreeRun}`，客户端据此问「最多能坐 N 个人一起，要不要拆开」。

副作用是会产生卖不掉的「奇数单座」—— 真实票务同样存在。

## 订单与支付

### 状态机的并发安全只靠一条 WHERE

全部流转经过同一个 CAS：

```sql
UPDATE t_order_order SET status = ? WHERE order_no = ? AND status IN (...)
```

影响行数为 1 就是本次生效，为 0 就是已被处理过 —— 重复消息天然幂等。
代码里**不允许出现没有 WHERE 条件的 `UPDATE t_order_order SET status = ...`**。

这一条 WHERE 就是订单并发安全性的全部落点。

### 支付幂等的四层

| 层 | 手段 | 拦什么 |
|---|---|---|
| L1 | 回调日志唯一键 | 渠道重复推送 |
| L2 | 支付单状态 CAS | 并发回调、乱序回调 |
| L3 | 渠道交易号唯一 | 同一交易号绑两个支付单 |
| L4 | 退款单 `uk_payment_no` | 重复退款 |

**L1 命中不能直接返回成功**：若首次插入成功但业务处理时崩溃，`process_status` 仍是 0；
重推时若因唯一索引冲突直接返回 success，这笔支付就永远丢了。所以 L1 只做日志去重，
业务幂等必须靠 L2。

### 为什么不全链路用 Seata

只有**改了会直接影响钱的**才走全局事务（G1 下单、G2 出票、G3 退款）。

把通知、统计、埋点塞进事务，会把事务从 50ms 拉到 500ms，锁冲突急剧放大 ——
而这些动作本来就可以重试、可以延迟。

### G2 的 `@GlobalTransactional` 曾经完全没生效

`markPaid` 被同一个类的另一个方法调用，**Spring AOP 代理被绕过，注解静默失效**。
没有报错、没有日志，只有一个没人会去找的缺失的 `Begin new global transaction`。

结果：支付可以提交而订单没有。修法是把事务方法抽到独立的 `PaymentTxService` ——
跨 bean 调用才会经过代理。

### 退款的钱到账了才释放座位

**否决：申请退款时就释放。** `REFUNDING` 是中间态，退款可能失败。若申请时就释放，
座位可能被 B 买走而 A 的退款又失败了 —— A 既没票也没钱，B 拿到了票，等价于超卖。

## 演出与电影

### 为什么演出不按电影的方式排期

生成器原本只有一个循环，同时服务电影和演出：遍历日期、场馆、时段，每个格子塞一个
合适的项目。

对电影完全正确 —— 电影院本来就是同一部片一天放很多场、连放几周。对演出是荒谬的：
**实测修改前，夏日回声演唱会同一天 12 场、跨 6 个场馆、一周 54 场**。每一场都是合法
数据，整个数据集描述的是一个一晚跑六个场馆的乐队。

电影是**排片**，演出是**定档**，这是两件事，现在分开生成。

### 为什么不让观众自己选座（大型演唱会）

两千个座位、十万人同时浏览座位图，不是任何人能提供的服务。所以场次分两种模式：
电影院观众自己挑，体育馆演唱会由系统按票档分配连座。

**分界线不是「影院 vs 场馆」，而是场馆属性与售卖政策的两个不同轴**：

- `t_event_place.seating_mode`（场馆）：这个地方**有没有**固定座位
- `t_event_session.seat_mode`（场次）：这次售卖**让不让**用户挑

一个有座位的体育场，`seating_mode` 是 SEATED，照样由系统分配座位。

### 场馆就是它的场地

场馆和场地曾经是两步创建，于是最自然的结果是**一个没有场地的场馆** —— 它排不了任何
演出、卖不了任何票，而在界面上它和「场地填错了」长得一模一样。

现在一次建完，一个事务。座位数**由模板算出来**（排数 ×（列数 − 过道列）− 损坏座），
不是填进去的 —— 填进去的那个只会和模板对不上。

## 抢购排队

### 为什么单独一个服务

并入 seat-service 的话，抢购流量会打穿到业务服务，失去隔离的全部意义。

### 为什么用 ZSet 不用 List

`ZADD` 的 member 唯一，**重复点击天然无副作用** —— 用户刷新一百次页面不会丢掉原来的
位置。用 List 就得自己判重。

### 放行系数为什么是 1.5

按 1:1 放行，被放进来的人有放弃的、有犹豫的、有超时的，结果票卖不完。按 10:1 放行，
9900 人排了半天队等一张从来就不存在的票。

1.5 是平衡点。而且**放行量按剩余票数算，不按队列长度算** —— 按队列长度算会让越卖不
出去的场次放得越快。

### 强制点在座位服务，不在网关

网关是**泄压阀，不是边界**。它从 query string 里读场次 id —— 那是调用方自己给的值 ——
所以谎报它的客户端能钻过去。

真正的执行点在座位服务：场次 id 来自它本来就在处理的请求，令牌拿由它派生出的 key 去
校验。已实测：**绕过网关直连座位服务同样被拒**。

### 售罄标记用 BITCOUNT，不另设计数器

计数器是第二份真相，锁座、释放、对账三条路径都要维护它，迟早漂移。

`BITCOUNT` 读的就是脚本刚写下的那些 bit，不会失步，而且 bitmap 从账本重建时会自愈。
代价是置位与扣减之间有毫秒级窗口 —— 但那个方向上多几个请求穿过网关是**无害的**，
反过来「提前标记售罄导致票卖不完」才是真损失。

## 基础设施

### Redis 挂了直接拒绝服务，不降级

降级到数据库行锁抢座会在瞬间打挂 MySQL，比拒绝服务更糟。宁可快速失败。

### 队列不落库

队列在开票后几秒灌满、几分钟清空。落库意味着多一张几乎永远为空的表，以及在最热的
路径上多一次写入。Redis 挂了排队本来也进行不下去。

### 定时任务用 `@Scheduled` 而非 XXL-Job

多一个组件的运维成本大于收益。多实例互斥用 ShedLock（Redis provider，不建表 ——
这套库是按服务分的，JDBC provider 意味着那张表要建两次、迁移要写两份）。

放行器是唯一的例外，它**刻意不加锁**：它的安全性来自 `queue_admit.lua` 的原子性，
加锁只会让人以为锁是它正确的原因。（这里原本靠 `ZPOPMIN`，但 Redisson 解不了那条命令
的返回，会静默丢成员，所以换成了脚本。）

### 订单超时：延迟消息为主，定时扫描为兜底，两个都要

只留定时扫描：最长 1 分钟延迟，用户对着一个按了没反应的支付按钮，座位也多占几十秒。
只留 MQ：消息不是保证送达的 —— 生产者可能在提交后、发送前崩掉，broker 也可能丢。
「这个座位能不能放出来」不该押在一条消息上。

两条路各自覆盖对方的失败模式，删掉任何一条，留下的那条就要独自承担它本来不打算承担的
失败。

**发送点放在 `@GlobalTransactional` 方法返回之后**，不在里面。Seata AT 模式下分支是各自
本地提交的，Spring 的 `afterCommit` 会在「本地已提交、全局还没定」的时刻触发 ——
那时发出去的消息，对应的订单仍可能被回滚。

**没用事务消息**：它解决的是「发送与本地事务原子」，做法是半消息加回查，而回查逻辑最终
只能问「订单表里有没有这一行」—— 和定时扫描兜底问的是同一个问题。多一套状态，
换同一个结果，否决它是因为它不解决新问题，不是因为它不好。

### 座位回收：按订单记到期时间，不给 key 加 TTL

锁了座却不下单的座位要能自己回来。最直觉的做法是给 bitmap 或 owner hash 加 TTL，
但那是**以场次为单位**的：一张 bitmap 上同时躺着几十个订单的占用，给整张 key 设过期时间
等于让先到期的那个订单决定所有人的命运。

到期本来就是逐订单的，那就逐订单地记（`seat:delay` 这个 ZSet 的 score），
由一个扫描任务去读。至于 `seat:order:{orderNo}` 上那个 2 小时的 TTL —— 它是兜底，
但它兜不住座位：那颗 key 一过期，释放脚本就不知道这个订单持有哪些座位了，
bit 永远没人清。

扫描任务需要一份「哪些场次值得扫」的名单，用 `seat:active` 这个集合，在加锁的 Lua 里
顺手登记。不这么做就只能 `SCAN seat:delay:*`，那是 O(整个键空间) 的，而且扫出来的
绝大多数键属于别的业务。退场也在 Lua 里做（`ZCARD` 为 0 才 `SREM`）—— 拆成两步的话，
一次并发的加锁可以恰好插在中间，于是那个新持有属于一个已经退场的场次，从此没人来收它。

### 管理接口放在各服务而不是独立 admin-service

场馆/项目/场次/票档都在 `maipiao_event`，归 movie-service 所有。单独建服务自己没有
数据，只能把每个操作 Feign 转发一圈 —— 多一跳、多一个部署，换不到隔离。

角色校验在网关统一做（`/api/*/admin/**` 必须是 ADMIN），不靠每个 controller 各自记得。

## 已知限制

不是遗漏，是有意的取舍：

| 限制 | 原因 |
|---|---|
| 没有分库分表 | 订单号用雪花 ID 预留了分片基因，但没有实际落地 —— 练手项目里落地分片只是增加噪音 |
| 没有真实支付渠道 | `PaymentChannel` 是策略接口，接支付宝沙箱只需新增实现类 |
| 管理后台不提供退款流程 | 改订单意味着动钱，那需要单独的流程和审计，不是一个通用编辑框 |
| 已售票的场次不能取消 | 取消意味着给所有人退款，是另一个量级的操作 |
| 实名观演没有采集流程 | 字段和限购逻辑在，但没有要求填写观演人 |
| 单机部署 | 没有 K8s / 多机房 / 灰度 |
| 压测是 2 万买家不是 100 万 | 一台 Windows 机加九个 JVM 承载不了百万并发客户端；见[压测报告](压测报告.md) |
