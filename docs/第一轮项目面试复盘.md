## 暴露的主要短板

1. **高并发回答停留在组件名。** “Redis、队列、限流”没有说明各自保护什么。限流控制进入的流量，排队安排准入顺序，Lua 保证一次多座位操作的原子性，数据库账本条件更新承担最终防超卖约束。
2. **锁座实现不熟。** bitmap 的 0/1 只表示可用性，还需 owner Hash 记录归属、ZSet 记录到期时间、订单座位集合支持释放。普通 Java 锁不能协调多个服务实例；分开的读位和置位存在竞争。
3. **幂等与唯一索引混淆。** 幂等是同一业务请求重复执行仍产生一次业务效果；唯一索引只是其中一道约束。稳定 lockToken、并发执行权、原请求参数校验和成功结果重放缺一不可。
4. **事务边界不清。** Redis 不属于 Seata AT 分支。本地事务不能自动回滚其他服务。UPDATE 影响 0 行本身不会抛异常，也不会自动触发回滚；代码必须检查并处理。catch 到异常不代表全局回滚完成。
5. **故障结果分类不足。** 请求超时可能已经成功；查不到一次订单不能证明失败。已确认回滚才能重试；结果未知应查询与对账，不能直接释放或启动第二次事务。
6. **支付与取消竞态需要练习。** 支付回调必须验签、核对渠道及金额、校验订单归属和状态；浏览器跳转不能作为支付凭证。取消后支付成功需要可靠退款补偿，退款超时也必须先查原退款单结果。
7. **排队实现不熟。** 有顺序的队列使用 ZSet，不能只靠 Set。准入令牌是服务端签发的短期购买资格，校验、删除和出队需要原子执行。
8. **安全要落实到服务端。** 隐藏后台入口只是界面体验。网关需清理外部身份头并注入可信身份；订单查询、取消、锁座释放仍需核验资源归属。直接访问内部端口需要部署隔离或服务认证。

## 对本轮讲解的校正

- Redis 支持 RDB/AOF，但故障切换、未刷盘数据、淘汰或误删仍可能丢状态。不能笼统说“内存数据库所以一定丢”。
- Redis bitmap 的某一位没有独立 TTL。订单座位集合过期也不会自动清 bitmap，且会丢掉释放所需索引。
- 原代码下单异常会立即释放 Redis 占座；“保留并重试”是本轮提出的改进，不应描述成原有能力。
- 当前订单过期扫描与取消状态机只处理 PENDING_PAY（0）；PAYING（1）不允许直接取消。后续需先核对渠道支付结果，再决定完成支付或关闭，不能直接把扫描条件扩展到 1。
- Seata 回滚可能重试，不能保证异常返回那一刻所有分支都已恢复。
- 本项目已有真实 RocketMQ 超时消息与定时扫描。选择 RocketMQ 可以联系延时消息和交易场景说明，但 Kafka 也能构建相应方案，不能说 Kafka 无法完成。
- 没有当前可复现的压测证据时，不要声称已经稳定支持十万人抢票；区分历史压测记录、设计目标和本次验证。
- 本轮“支付后端会核验金额”不能仅根据回答认定已实现。代码复查发现原支付单直接使用客户端金额，本次才改为读取订单快照并核验归属、状态、金额和固定期限。

## 本轮之后落实的改进

已根据《优化建议-下单失败与座位保留》修改预约、下单、清扫与结算页：固定首次截止时间，持久化同 token 的处理资格和全局事务 XID；确认回滚后保留座位供手动重试，结果未知时禁止重复创建和释放；成功后返回原订单当前状态。支付入口补充服务端快照核验，取消释放前补充 Seata 全局锁检查。

这些是本次协助完成的代码，不等于已经独立掌握。下一轮应能逐段解释新状态机、事务边界和测试用例；验证结果、迁移步骤及 TC 历史缺失等剩余限制详见优化文档。
