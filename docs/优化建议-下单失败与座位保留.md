# 下单失败后的座位保留与幂等重试

日期：2026-10-24。状态：核心代码已实施；验证范围与剩余限制见第 7、8 节。

## 1. 问题与目标

原创建流程在捕获异常后尝试释放 Redis 锁座。临时数据库或优惠券服务故障可能让用户失去刚选中的热门座位；请求超时也可能已经提交成功，不能把异常一律理解为失败。

本次实现：首次锁座确定固定期限；确认回滚后保留原座位，用户可用同一 token 手动重试；成功时返回原订单的当前状态；事务结果未决时禁止重复创建和到期释放。该策略适用于本学习项目，不代表所有票务平台的统一实现。

Redis 不参与 Seata AT，跨系统操作并非一个原子事务。正确性依赖持久化协调状态、数据库约束、全局事务结果核对、Redis owner 校验及重复清扫。

## 2. 已实施的流程

1. seat-service 生成稳定的 lockToken 和绝对截止时间 expiresAt，先向 order-service 登记 PREPARING，再执行 Lua 锁座，最后发布服务端实际座位和标签成为 RESERVED。自动配座与手动选座使用相同流程。
2. order-service 校验用户、场次和规范化座位集合。lockToken 同时作为订单号，沿用订单号唯一索引。
3. 开启 G1 后暂时解绑 XID，在独立自动提交的数据库操作中将预约 CAS 为 PROCESSING，并记录 XID 和请求摘要；取得资格之后才能调用业务分支。协调入口禁止加入 Spring 本地事务，防止记录随业务一起回滚。
4. G1 协调场次库存、数据库座位账本、优惠券、订单及明细。业务方法检查影响行数，前端座位标签、优惠金额不作为权威数据；锁券分支返回实际优惠金额。
5. 全局提交确认后写 SUCCEEDED。明确回滚完成后写 RETRYABLE，Redis 座位保留至原截止时间。提交超时不反向发起 rollback，查询原 XID 确认结果。
6. 查单和同 token 重放均返回原订单的当前状态；不会把已经支付、取消或退款的订单变成新的待支付订单。
7. 用户退出、座位到期清扫先申请关闭预约。关闭和取得下单资格使用同一行 CAS，避免清扫后旧请求继续创建。PROCESSING 不允许关闭。
8. 已创建订单需走取消事务，数据库库存、账本和优惠券幂等回收成功后，再以 GlobalLock + FOR UPDATE 检查全局锁，确认取消结果后才能释放 Redis。Redis 故障保留到期索引，后续重复清扫。

## 3. 协调状态与结果分类

预约状态与订单支付状态是两套状态，不可混用。

| 预约状态 | 含义 | 允许的动作 |
| --- | --- | --- |
| PREPARING | 已登记，锁座与发布尚未完成 | 发布；到期或主动放弃后关闭 |
| RESERVED | 服务端座位已登记 | 未到期可申请下单；放弃或到期可关闭 |
| PROCESSING | 已取得资格，G1 结果尚未持久化 | 查原 XID；禁止重试与释放 |
| RETRYABLE | 已确认 G1 回滚 | 在原有效期内核验持有后手动重试，或明确调整优惠券 |
| SUCCEEDED | 已确认创建提交 | 返回原订单当前状态；取消由订单状态机处理 |
| CLOSED | 无未决创建，预约已关闭 | 按归属释放 Redis；可重复执行 |
| RELEASED | 已确认执行关闭后的释放调用 | 保留历史，拒绝重用 token |

TC 的 Committed / AsyncCommitting 视为已决定提交；Rollbacked / TimeoutRollbacked 视为回滚完成。Finished、查不到、TC 不可用及其余未终结状态均不作为成功或失败证明。

不采用到期即可接管的执行租约。旧 XID 未确认回滚时，即使预约已过原截止时间，也不能开启第二次 G1 或释放座位。finish 同时匹配状态与 XID，阻止旧事务结果覆盖新一次尝试。

请求摘要绑定场次、排序后的座位和优惠券。用户、场次和座位不能替换；修改优惠券仅在 RETRYABLE 且请求显式 revise=true 时允许。前端金额不进入摘要，因为它不参与后端计价。

## 4. 时间、支付与释放约束

- 首次 expiresAt 由服务端确定，刷新、查单、重试不续期；订单 lockExpireTime 使用同一截止时间。
- Lua 使用 Redis TIME 拒绝已经到期的锁座或配座操作。应用、数据库和 Redis 仍需保持时钟同步。
- 支付服务先读取订单服务快照，核验所属用户、可支付状态、订单期限，金额来自订单 payAmount。保留旧 amount 参数兼容客户端，但忽略其计费值。
- 支付单到期时间取“本地支付有效期”和“订单截止时间”的较早值。旧支付单若金额、归属或期限不匹配，拒绝静默复用或重新开单，需核对原支付结果。
- 新订单的预约必须是 SUCCEEDED 才能提供支付快照或接受订单已支付分支，防止 G1 一阶段可见行被误用于支付。迁移前的历史订单允许没有预约记录。
- 普通释放不触碰 SOLD:token。Lua 仅清理匹配当前 owner 的座位，重复释放及迟到的旧释放请求不会清掉新持有者。
- 订单座位 Set 不再有独立的两小时 TTL。旧数据已丢 Set 时，释放脚本按 owner Hash 查找同 token，防止永久占用；大场次的 Hash 全量扫描成本需继续评估。
- PREPARING 期间进程失败由预约恢复任务到期关闭并回收；孤儿 token 写 CLOSED 墓碑阻断迟到登记。

## 5. API 与前端行为

公共接口经网关访问：

| 接口 | 行为 |
| --- | --- |
| POST /api/order/create | 使用原 lockToken 创建；返回 CreationResult，包含 state、expiresAt、heldVerified、orderNo、payAmount、expireTime、orderStatus、message |
| GET /api/order/requests/{token} | 仅所属用户可查询；核对原全局事务，成功时返回原订单 |
| 原公共锁座释放接口 | 核验用户归属并请求关闭；处理中或已支付拒绝释放 |
| POST /api/pay/precreate | 按服务端订单快照校验，客户端金额不作为收款依据 |

内部 /inner/reservation/prepare、publish、close 供座位服务调用；/inner/{orderNo}/summary 返回已确认创建的支付快照。内部接口仍依赖网关封禁和部署隔离，不能将服务端口直接公开。

前端在 POST 前将 token、原请求及截止时间保存到 sessionStorage；刷新先查单，网络异常不清掉 token。只有 RESERVED/RETRYABLE、服务端确认 heldVerified、且未到期时允许提交。结果未知时最多自动退避查询 6 次，之后保留手动查询入口；不自动重新创建订单。

退出结算先请求服务端关闭，再清理本地记录。旧版本找不到预约时提示先查“我的订单”，并提供重新选座入口；清理浏览器记录本身不会释放服务端座位。

创建成功和成功查单会投递超时消息；重复消息由状态机幂等处理，发送失败仍由定时扫描兜底。座位清扫默认 30 秒，预约恢复默认 30 秒、每轮 200 条，按 update_time 轮转，避免一批未决请求长期占据全部扫描名额。

## 6. 数据库迁移与发布

新增脚本：docs/sql/schema/07_order_reservation.sql，仅创建 maipiao_order.t_order_reservation，不删除既有订单或数据卷。

- 新装：原 Docker 初始化目录会读取新增 SQL。
- 已有数据库：**必须先手动执行该脚本**；Docker 对已有数据卷不会重新执行初始化 SQL。
- 参与全局事务的库仍必须具备 05_seata_undo_log.sql 中对应的 undo_log，且服务使用 Seata 代理数据源。
- 建议维护窗口发布：暂停新选座和下单，等待正在执行的旧事务结束、排空或核对旧预约；先建表，再协调更新 order/user/seat/pay 服务及前端，恢复流量。此次修改包含返回契约变化，不建议让新旧版本长期混跑。
- 旧优惠券锁定接口返回值也有变化，订单与用户服务必须配套更新。旧订单无预约记录可继续支付/取消；旧锁座不能直接在新结算页下单，应核对旧订单后重选。
- 回退时暂停流量并先核对新增 PROCESSING 记录，不应直接回退为按到期时间无条件释放。

本次只修改代码与测试，不对用户开发数据库执行迁移，不部署服务。

## 8. 剩余边界与后续事项

1. **TC 历史记录缺失时需要人工核对。** 若进程在 TC 完成与协调结果持久化之间退出，且 TC 后来不再保留该 XID，当前实现保持 PROCESSING 并保留座位；它不能自动证明最终结果。本轮没有实现人工裁决工具，也不能承诺所有异常会自动恢复。排障需同时核对 TC、分支 undo_log、订单、库存账本及优惠券；未确认前不要直接删 Redis、改 RETRYABLE 或重建订单。
2. **PAYING 渠道核对仍需完善。** 超时状态机只取消 PENDING_PAY（0）；不能直接将 1 加入取消 SQL。支付与取消竞态、渠道已收款但本地未确认，需要完整渠道查单、关单和退款对账。本轮固定了本地支付期限，并未改造所有渠道协议或实现真实支付宝。
3. **协调记录清理未实现。** PROCESSING 和 CLOSED 未完成释放的记录不可按普通 TTL 删除；成功与终态历史也需满足幂等重放及审计保留期后再归档，不能直接删除导致稳定 token 可重用。
4. **故障信息目前以通用状态呈现。** 确认回滚统一 RETRYABLE，未持久化具体业务拒绝原因；优惠券失败允许明确修改后重试，后续可补充更细错误码与用户提示。没有自动重试业务创建。
5. **锁座响应丢失仍可能产生短暂孤儿占用。** 用户未收到 token 时无法主动恢复，但 PREPARING/RESERVED 登记及到期清扫负责回收。Redis 整库数据丢失后的安全重建属于原系统另外的故障恢复课题。
6. **尚无本轮高并发端到端压测结论。** 数据库 CAS 并发测试不等于十万人同时抢票的吞吐验证；完整服务重启、网络分区、消息重投和浏览器真实交互仍需专项演练。
7. **Seata 服务端持久化仍为原开发配置。** file 模式不等于跨容器重建可恢复的生产部署，正式运行应配置持久卷或 DB 存储、备份及告警；本轮未修改生产运维架构。

## 9. 面试表述

> 我发现原流程下单异常后立即释放座位，可能导致用户在临时故障后丢座，因此实现了固定期限的预约保留。用稳定 token 绑定用户、场次和座位，通过数据库 CAS 仲裁创建与清扫；Seata 确认回滚后才允许重试，成功后重放原订单，事务结果未知时持续查询并禁止释放。Redis 不参与全局事务，所以释放必须放在数据库结果确认之后。当前对 TC 历史缺失仍需要人工核对，并未声称所有故障都能自动修复或已经支持十万人抢票。
