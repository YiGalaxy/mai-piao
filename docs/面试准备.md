# 麦票项目面试准备与学习路线

这份文档以当前代码为准，目标是帮助你在 Java 实习生面试中把项目讲清楚，而不是背技术名词。

## 一、项目定位

麦票是一个电影和演出票务系统。项目没有把重点放在普通 CRUD，而是围绕五个问题设计：

1. 多个用户同时选中同一个座位时，如何保证不超卖。
2. 下单涉及多个服务和数据库时，如何保证事务一致性。
3. 支付回调重复、乱序、延迟到达时，如何保证只出票一次。
4. 2000 张票面对大量请求时，如何在入口处削峰和快速失败。
5. Redis、数据库或消息队列出现短暂故障时，如何补偿和恢复。

面试时可以这样概括：

> 我做了一个基于 Java 微服务的票务系统，重点实现了 Redis Bitmap 加 Lua 原子锁座、MySQL 座位账本、Seata 分布式事务、支付回调多层幂等，以及 Redis ZSet 抢购排队。订单超时目前使用定时扫描；RocketMQ 已配置但尚未接入业务生产消费。项目的核心是并发、事务和一致性边界。

## 二、当前实际架构

当前代码实际包含 8 个运行单元：

| 模块 | 作用 |
|---|---|
| gateway | 路由、JWT 认证、角色校验、抢购流量入口 |
| user | 用户、登录、优惠券、角色 |
| movie | 影片、影院、影厅、排片、MySQL 座位账本 |
| seat | 查座位、锁座、释放、连座分配 |
| order | 下单、订单状态机、取消、退款申请 |
| pay | 支付单、回调、出票、退款 |
| queue | 抢购排队、分批放行、售罄判断 |
| mock-pay | 模拟第三方支付，可生成重复、乱序、失败回调 |

服务间调用使用 OpenFeign，接口定义在各调用方服务的 `feign` 包中；`maipiao-api`
目前只是空目录。服务发现和配置使用 Nacos，负载均衡使用 Spring Cloud LoadBalancer。

数据库按服务划分 schema：用户、**项目/场次**、订单、支付分别使用
`maipiao_user`、`maipiao_event`、`maipiao_order`、`maipiao_pay`；座位服务没有独立
数据库，Redis 负责实时占用，`maipiao_event.t_event_session_seat` 是持久账本。

## 三、完整购票链路

### 1. 浏览

用户端请求 Gateway。影片、影院、排片和座位图属于公开读接口，订单、支付和管理接口需要 JWT。

### 2. 锁座

`seat-service` 接收座位索引后执行 Redis Lua：

```text
检查所有 seat_index 是否空闲
如果有一个冲突，整个请求失败
如果全部空闲，一次性设置 Bitmap、owner、过期队列
```

Bitmap 只回答“这个位置是否被占用”，owner Hash 记录“被哪个订单占用”。

### 3. 下单

用户提交锁座 token。`order-service` 先确认 Redis 中的锁仍属于该订单，再启动 Seata 全局事务：

```text
占用场次库存 -> 锁定优惠券 -> 写订单 -> 写订单明细
```

Redis 锁座不放进 Seata，因为 Redis 不是 Seata AT 的数据库分支；事务失败时通过补偿接口释放锁座。

### 4. 支付和出票

支付回调先验签，再写回调日志。业务处理使用支付状态 CAS：只有处于可支付状态的订单才能变成已支付。

出票事务完成：

```text
支付单成功 -> 订单变成已支付 -> MySQL 座位账本变成已售
```

Redis 的锁定标记在事务成功后再转为已售，避免数据库回滚后 Redis 留下无法释放的脏数据。

### 5. 超时和退款

- `OrderTimeoutJob` 的 `@Scheduled` 扫描触发未支付订单取消。RocketMQ 延迟消息
  属于已配置但尚未接入的后续方案。
- 取消时释放库存、优惠券和 Redis 锁座。
- 退款只有渠道确认成功后才释放已售座位，避免钱没退回来就把座位重新卖掉。

## 四、技术栈和学习重点

### Java 和 Spring

- Java 21
- Spring Boot 3.2.12
- Spring Cloud 2023.0.3
- Spring Cloud Alibaba 2023.0.3.2
- Maven 多模块
- MyBatis-Plus

学习重点：依赖注入、事务、AOP、配置绑定、模块依赖、Feign 调用和 Spring 生命周期。

### 微服务

- Spring Cloud Gateway：统一入口和过滤器
- Nacos：注册中心、配置中心
- OpenFeign：服务间调用契约
- LoadBalancer：服务实例选择
- Seata 2.2.0：跨服务数据库事务

面试重点不是“用了 Nacos”，而是要说明：服务为什么拆分、哪些调用必须同步、哪些状态可以异步、哪些数据不能跨库 JOIN。

### Redis 和高并发

- Bitmap：大量座位状态的紧凑存储
- Hash：座位归属
- ZSet：过期扫描和抢购排队
- Lua：把检查和写入合并成原子操作
- Spring Data Redis：访问 Redis；Redisson 已列为依赖，但当前锁座不使用它

面试中要能解释为什么不用数据库行锁：热门座位会把大量请求堆到 MySQL；Redis Lua 可以让冲突请求快速失败，MySQL 只保留账本和最终业务状态。

### 数据库和一致性

- MySQL 8.0
- MyBatis-Plus
- 唯一索引
- 条件更新 CAS
- 版本字段
- 按服务 schema 隔离

要记住：Redis 是高并发实时状态，MySQL 是可恢复账本。当前有冷位图播种与部分补偿，
**尚未实现完整自动化对账任务**。

### 消息队列

- RocketMQ 5.3.1 已在 Compose、POM 和配置中准备
- 当前无业务消息生产者或消费者，也没有延迟消息关闭订单的代码
- 后续学习重点：延迟消息、消费幂等、重试和定时扫描兜底

当前订单超时关闭由数据库定时扫描完成。若以后引入 RocketMQ，消费端仍需检查订单
当前状态，不能只相信消息到达时间。

### 安全

## 五、最重要的面试问题

### 为什么 Redis Bitmap 不会超卖？

因为检查和设置由同一个 Lua 脚本在 Redis 单线程中执行，中间不会插入另一个请求。MySQL 的座位表还会通过状态条件更新再次拦截并发写入。

### 为什么不用分布式锁？

分布式锁会把高并发请求串行化，而且锁的粒度和释放异常都比较难处理。Lua 可以一次处理多个座位，更适合“批量检查、批量占用”。

### Seata 能不能回滚 Redis？

不能。Seata AT 主要管理数据库资源，所以 Redis 锁座必须在全局事务前完成，失败后使用补偿释放；这也是项目中最终一致性的重要边界。

### 支付回调为什么要做多层幂等？

回调可能重复、乱序、延迟，单一的“是否处理过”字段不够。项目同时使用回调日志唯一键、支付状态 CAS、渠道交易号唯一约束和退款单唯一约束。

### 为什么支付成功后还要确认 Redis 座位？

锁定和已售需要区分。支付成功后如果 Redis 仍然只是普通锁定，退款释放、售罄统计和后续对账都会出现问题。

### 如何处理支付回调和订单超时取消的竞争？

两条路径都通过订单状态机的条件更新竞争状态。只有影响行数为 1 的更新生效，另一条路径发现状态已变化后按幂等逻辑结束。

### 为什么要有 queue-service？

网关只负责入口，queue-service 负责把抢购用户放进 ZSet，并按剩余票数分批放行。这样大量无效流量不会直接冲击座位、订单和数据库。

## 六、推荐学习顺序

### 第一阶段：Java 和 Spring 基础

掌握依赖注入、AOP、事务传播、异常处理、配置文件、MyBatis-Plus 和 REST API。

### 第二阶段：Redis 高并发

按项目顺序学习 String、Hash、Set、ZSet、Bitmap、Lua，再理解 Redis 单线程、持久化、过期键和缓存一致性。

### 第三阶段：微服务

学习 Gateway、Nacos、Feign、LoadBalancer，并亲自画出服务调用图和数据库边界。

### 第四阶段：事务和消息

先掌握本地事务，再学习 Seata AT 的全局事务；结合现有 `@Scheduled` 扫描理解
超时取消。RocketMQ 延迟消息、重复消费和消息补偿属于后续练习。

### 第五阶段：项目核心源码

重点阅读：

- `SeatBitmapService`
- `seat_lock.lua`
- `OrderService`
- `OrderStateMachine`
- `PaymentService`
- `PaymentTxService`
- `AdmissionDispatcher`
- `JwtAuthFilter`

### 第六阶段：测试和故障演练

至少演示四个场景：两人抢同一座位、重复支付回调、支付和超时取消竞争、Redis 座位图重建。

## 七、面试演示顺序

建议准备 5 分钟演示：

1. 登录并展示 JWT 鉴权。
2. 浏览场次和座位图。
3. 选择座位并创建订单。
4. 通过 Mock Pay 触发成功回调。
5. 重复触发同一个回调，展示不会重复出票。
6. 展示订单、支付单、座位账本状态。
7. 运行抢购压测，展示锁座不重复分配和售罄快速失败；它不覆盖下单与支付。

先讲问题，再讲技术：

```text
问题：同一座位不能被两人占用
方案：Redis Bitmap + Lua 原子锁座
兜底：MySQL 座位账本 + 条件更新
结果：已有压测在锁座阶段无重复分配；完整支付链路仍需集成测试
```

## 九、当前项目边界

这是一个学习和面试项目，不要把它描述成生产级系统。当前仍需要继续完善：
